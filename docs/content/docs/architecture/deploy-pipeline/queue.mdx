| Mechanism | What it is | Rule |
|---|---|---|
| <Term id="deploy-queue">Deploy queue</Term> | The deploys of one service with the status `queued` | A deploy waits for its turn. |
| <Term id="deploy-worker">Deploy worker</Term> | A background task, one per service | Two deploys of one service never overlap. |
| <Term id="build-slot">Build slot</Term> | The right to build one image | The server runs `--build-concurrency` builds at a time (default 2). |

## Only the newest deploy matters

A new deploy cancels the older deploys of the same service that wait in the queue. Their reason is `superseded by dep-…`.

If a deploy waits in the queue, a restart request merges into that deploy. It adds no deploy, because that deploy starts with the current settings.
