The <Term id="deploy" /> first takes the [service lock](/docs/architecture/deploy-pipeline/lock) and saves the [snapshot](/docs/architecture/deploy-pipeline/snapshot). Then it starts the instances. The state of the deploy is `deploying`.

```text title="Deploy log" noCopy
==> Limits: 512 MiB memory, 1 CPU per instance
```

## What each container gets

| Setting | Value |
|---|---|
| Network | The <Term id="private-network" />, with the service name as <Term id="alias">DNS alias</Term> |
| <Term id="restart-policy">Restart policy</Term> | `unless-stopped` |
| <Term id="published-port">Published port</Term> | `127.0.0.1:<random port>`. See [Why 127.0.0.1](/docs/architecture/networking-model/why-localhost). |
| Memory | The memory limit, with no swap above it |
| CPU | The CPU limit |
| Processes | `--pids-limit` |
| Logs | Log rotation (`--log-max-size`, `--log-max-files`), when the default log driver of the Docker daemon is `json-file` |

<Accordions>
  <Accordion title="A CPU limit that the host cannot give">
    - If the CPU limit is above the CPU count of the Docker host, the engine lowers it to that count. It writes a warning in the deploy log.
    - On a host whose kernel has no CPU CFS quotas, the engine sets no CPU limit. It writes a warning too.
  </Accordion>
</Accordions>
