The <Term id="proxy" /> routes by the `Host` <Term id="header" />. On the request path, it never calls the <Term id="engine" /> or the database. It reads the <Term id="route-table" />, which gives the <Term id="upstream">upstreams</Term> of each hostname.

An upstream is always a port on `127.0.0.1`. The [networking model](/docs/architecture/networking-model/why-localhost) tells you why.

## If no instance can answer

| Case | Answer of the proxy |
|---|---|
| Unknown host | A 404 page |
| Suspended service | A 503 page |
| No healthy instance | A 503 page with `Retry-After` |

See [Errors of the proxy](/docs/architecture/networking-model/proxy-errors).

## The crates

| <Term id="crate">Crate</Term> | Contents |
|---|---|
| `ferry-proxy` | The `RouteTable`, the HTTP/1.1 and HTTP/2 reverse proxy with <Term id="round-robin" /> load balancing, websockets, error pages, <Term id="tls" /> termination and connection limits. |
| `ferry-tls` | Automatic HTTPS: <Term id="acme" /> HTTP-01 certificates (Let's Encrypt by default), their storage and renewal, and <Term id="sni" /> resolution for the proxy. |

<Accordions>
  <Accordion title="How the proxy uses ferry-tls">
    The proxy does not depend on `ferry-tls`. It calls the `TlsHooks` <Term id="trait" /> for two things: the answers to ACME challenges, and to know if a host has a certificate. It does the TLS work with the certificate resolver that `ferryd` gives it. See [HTTPS](/docs/architecture/networking-model/https).
  </Accordion>
</Accordions>
