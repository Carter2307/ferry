Ferry is built for one team running its own server. A server has one administrator account: whoever signs in with it, or holds one of its API tokens, controls the whole server. There are no other users, roles or per-service permissions. The model below keeps the account, the tokens and the secrets behind them on the server, keeps everything but the proxy off the network, keeps one runaway app from taking the server down, and keeps two Ferry servers from ever damaging each other's workloads.

## The account

- **One administrator account per server:** an email and a password of at least 8 characters. The server stores an Argon2id hash of the password, never the password.
- **Created with a setup code.** While the server has no account, the `ferryd` banner and `ferryd status` end with `Create your account: http://127.0.0.1:7878/setup?code=<code>`, where the code is 24 random hex characters, also kept in `<data-dir>/setup_code` with mode `0600`. Creating the account takes the code, so only someone who can read the server's terminal or its data directory can create it. The file is deleted once the account exists, and creating the account signs that browser in.
- **The session is a cookie the page can't read.** Signing in at `/login` sets the session cookie: `HttpOnly`, `SameSite=Strict`, and `Secure` when the dashboard is reached over HTTPS through a proxy. Its name ends with the port of the address you use (`ferry_session_7878`), so two servers on one host name, such as `127.0.0.1:7878` and `127.0.0.1:7879`, keep a session each. The dashboard's JavaScript can't read it, and nothing but UI preferences is kept in `localStorage`. The server stores only the SHA-256 of the session's secret.
- **A session ends** 30 days after it was last used, when you sign out, or, for every other browser, when the password is changed. **Server → Account** in the dashboard lists the sessions and can sign each browser out.
- **Changes must come from the dashboard itself.** A `POST`, `PUT`, `PATCH` or `DELETE` request authenticated by the cookie must come from the dashboard's own origin: the server checks `Sec-Fetch-Site`, or else `Origin` against the host. Otherwise it answers 403 `cross_site_request`.
- **Failed sign-ins are limited.** After 10 failures within 5 minutes, sign-ins and setup attempts are refused with 429 `too_many_attempts` until the oldest failure is 5 minutes old. The limit counts for the whole server, not per IP address, so someone who can reach the API can delay the administrator's sign-in: one more reason to keep the API on localhost or behind HTTPS.
- **A forgotten password is replaced on the server.** [`ferryd reset-password`](/docs/reference/server-options#ferryd-reset-password) asks for a new password twice without echo (or reads one line from standard input when it isn't a terminal), replaces the password and signs every browser out. It works while the server runs, and API tokens keep working.

## API tokens

The CLI, scripts and CI authenticate with API tokens: `fy_` followed by 40 hex characters.

- **Named, with an optional expiry.** You create them under **Server → Account** in the dashboard. A token is shown once, when it is created: the server stores its SHA-256 digest, and lists it with its last 4 characters and when it was last used. Revoking a token stops it at once.
- **`ferry login` gets one for its terminal.** It prints a page of the dashboard and a code such as `ABCD-EFGH`, and waits. Signed in to the dashboard, you check that the page shows the same code and who asks, then approve or deny. The terminal then receives a token of its own, named after it (`user@host`), listed and revocable like the others. A request expires after 10 minutes.
- **Full access, except to the account.** A token can read every variable and every datastore password through the API, and deploy, delete or run anything. Treat it like a root password. It can't use the account endpoints (`/api/v1/auth/…`: the password, the sessions, the tokens, approving a `ferry login`): those only accept the dashboard's session and answer 403 `session_required` to a token.
- **Header first.** `Authorization: Bearer <token>`. `?access_token=` is accepted on `GET` requests only, for browser `EventSource` streams; `ferryd`'s request log records paths without their query string.
- **On the client side,** `ferry login` saves the server and token in `~/.config/ferry/config.json` (or `$XDG_CONFIG_HOME/ferry/config.json`) with mode `0600`, in a `0700` directory.

Every `/api/v1` request, unknown routes included, needs an API token or the session cookie. The exceptions are the `/api/v1/auth` routes a browser or a terminal calls before it is authenticated: `status`, `setup`, `login`, `logout`, and the two calls with which a terminal starts a `ferry login` and collects its token.

### The server token

`ferryd` also has a token of its own. It generates it on first start and stores it in `<data-dir>/api_token` with mode `0600`; `--api-token` / `FERRY_API_TOKEN` sets it explicitly instead (the environment value is hidden from `ferryd --help`).

- It authenticates the API like the other tokens, so CLI logins and CI jobs that already use it keep working. It is compared in constant time (both sides are hashed with SHA-256, then compared without early exit).
- It is never printed, isn't listed in the dashboard and can't be revoked there.
- It is meant for scripts on the server itself:

```bash title="Terminal"
FERRY_TOKEN="$(cat /var/lib/ferry/api_token)" ferry services
```

To rotate the server token, restart `ferryd` with a new `--api-token`, or stop it, delete `<data-dir>/api_token` and start it again to generate a new one. Then give the new token to whatever used the old one.

## Exposure

| Listener | Default | Reachable from |
|---|---|---|
| API and dashboard (`--api-addr`) | `127.0.0.1:7878` | The server itself only |
| Proxy (`--proxy-addr`, `--https-addr`) | `0.0.0.0:8080` | Everywhere: this is the public edge |
| App containers | `127.0.0.1:<random>` | The server itself only; the public reaches them through the proxy ([why](/docs/architecture/networking-model#why-127001-published-ports)) |
| Datastores | `127.0.0.1:<fixed port>` | The server itself only |

The proxy can also serve the dashboard and the full API on a hostname (`--dashboard-host`). By default that is `ferry.<base-domain>` only when the base domain is local (`localhost`, `.local`, `.internal`, `.test`, an IP address), and off on a public domain, where you must enable it explicitly. Only do so with HTTPS (`--https-addr` and `--acme-email`): over plain HTTP the password, the session cookie and API tokens would cross the network in clear text. The safer default for a production server is to keep the API on localhost and reach it through an SSH tunnel:

```bash title="Terminal"
ssh -L 7878:127.0.0.1:7878 you@your-server
ferry login --server http://127.0.0.1:7878
```

Connecting a [domain](/docs/guides/domains) to a server that still has a local base domain doesn't change this: the dashboard stays where `--dashboard-host` put it. On a public server started without `--base-domain`, that is `ferry.localhost` on the public proxy, which anyone can ask for by sending that `Host` header. Start such a server with `--dashboard-host none`, or with a hostname of your own and HTTPS.

The proxy answers one path for any host, without authentication: `/.well-known/ferry-domain-check/<token>`, which Ferry uses to verify that a domain reaches this server. The answer is the token, which must be alphanumeric, followed by an id made up when the process started. It says nothing about the services.

To show the DNS records of a domain, a server behind NAT asks a public service which IPv4 address it has (`api.ipify.org`, then `ipv4.icanhazip.com`, then `checkip.amazonaws.com`). It is the only request Ferry makes to a third party on its own, it only happens once a non-local domain exists, and `--public-ip` replaces it.

A few endpoints need no authentication because they reveal nothing secret: `/healthz`, the OpenAPI document (`/api/openapi.json`), Swagger UI (`/api/docs`, which asks for an API token to send requests), and the dashboard's static files (the dashboard asks you to sign in to show anything). Dashboard and Swagger UI pages are sent with `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` and `X-Content-Type-Options: nosniff`. `ferryd` sends no CORS headers, so other origins can't call the API from a browser.

See [Production setup](/docs/guides/production) for a complete hardened setup.

## The data directory

`--data-dir` (default `./ferry-data`) holds everything Ferry knows, including secrets: variable values, datastore passwords, repository URLs with credentials, the secrets of connected GitHub and GitLab accounts, logs, uploaded source code and TLS keys. `ferryd` therefore creates it with mode `0700` (owner only) and tightens it at every start.

| File | Mode | Contains |
|---|---|---|
| `api_token` | `0600` | The server token |
| `setup_code` | `0600` | The setup code, only while the server has no account |
| `instance_id` | `0600` | This data directory's claim on its Docker name prefix |
| `ferry.db` | inside the `0700` directory | Services, deploys, variables, datastores (with passwords), env groups, git connections (with their secrets: a GitHub App's private key, tokens, an OAuth application's secret), settings, the account (with the hash of its password), its sessions and API tokens (as SHA-256 digests) |
| `certs/<host>/key.pem`, `certs/accounts/*.json` | `0600` | TLS private keys and the ACME account |
| `logs/`, `repos/`, `uploads/`, `builds/` | inside the `0700` directory | Deploy and job logs, git mirrors, uploaded archives, build scratch space |

<Callout type="warning" title="Secrets are not encrypted at rest">
Variable values, datastore passwords and the secrets of connected git accounts are stored in plain text in `ferry.db`, protected by the directory's permissions. Anyone who can read the data directory, or its backups, can read every secret. Encrypt backups and restrict access to the machine accordingly.
</Callout>

## Secrets

How Ferry keeps secret values out of places where they tend to leak:

- **Builds.** Variables reach `docker build` as BuildKit secrets (`--secret id=KEY,env=…`), with the values passed through the Docker CLI's environment, never its command line. Generated Dockerfiles mount them only into their install and build steps and never declare them as `ARG`s, so they don't end up in the image or its history. Your own Dockerfile can mount them the same way with `RUN --mount=type=secret,id=KEY,env=KEY …`. For compatibility, your Dockerfile also receives `--build-arg KEY` for the `ARG`s it declares, and BuildKit records those in the image history: declaring a secret as `ARG` is the Dockerfile's choice.
- **References instead of copies.** [Env var references](/docs/reference/env-references) such as `${{datastore.app-db.password}}` keep the password in one place; the service stores the reference and gets the value only in its containers.
- **Repository credentials.** A token embedded in a repository URL (`https://user:token@github.com/…`) is redacted as `***` in deploy logs, error messages, blueprint change lists and webhook responses. Git receives credentials through its environment, never its command line, and only hands them to the repository's own host: a redirect to another host gets none.
- **Git connections.** A [connected GitHub or GitLab account](/docs/guides/git-accounts) is authorized on the provider's own page, for read access only: a GitHub App that reads the repositories you chose (`contents: read`, `metadata: read`), or a GitLab application with the `read_api` and `read_repository` scopes. What the server keeps for it (the app's private key, the OAuth tokens and client secret, or a personal access token) is never returned by the API: of a personal token, a connection shows `token_hint`, its last characters. A GitHub App's tokens last an hour and are only kept in memory. Ferry sends a token to its provider's API and, when cloning or listing branches, to repositories on the provider's own host (same scheme, host and port): a repository elsewhere is read without it. The answers the provider sends back through the browser are only accepted with a single-use random `state` the server issued less than an hour before.
- **Datastore passwords** are generated (32 random characters) and never appear in logs or error messages. Readiness probes never put them on a command line: `redis-cli` gets the password through the exec environment (`REDISCLI_AUTH`).
- **Webhook responses** return deploys with credentials redacted and without server paths.

The API returns variable values and datastore passwords to whoever is authenticated, with the session or an API token: the dashboard shows them so you can copy connection strings.

## Webhooks

Webhooks don't use the account or an API token; each has its own secret:

- **Deploy hooks** are secret URLs (`/hooks/deploy/<service id>?key=<key>`). The path takes the service id only, since names are guessable, and an unknown id and a wrong key get the same 401, so the hook can't be used to discover services. Anyone with the URL can trigger deploys (but nothing else): rotate it with `ferry deploy-hook rotate NAME` if it leaks.
- **GitHub webhooks** are disabled (404) until `--github-webhook-secret` is set. Each delivery must be signed with it (`X-Hub-Signature-256`, HMAC-SHA256 over the raw body, checked in constant time), and a delivery whose body or delivery id was already processed is ignored, so a captured delivery can't be replayed.

Details are in the [API overview](/docs/reference/api-overview#webhooks).

## Proxy headers

The proxy is the edge, so it can't trust forwarding headers sent by clients. Before forwarding a request, it drops every client-supplied `Forwarded`, `X-Forwarded-*`, `X-Real-IP`, `Forwarded-For`, `Front-End-Https`, `X-Url-Scheme`, `X-Client-IP` and `X-Cluster-Client-IP` header, then sets:

| Header | Value |
|---|---|
| `X-Forwarded-For`, `X-Real-IP` | The address of the connection's peer, and nothing else |
| `X-Forwarded-Proto` | `http` or `https` |
| `X-Forwarded-Host` | The `Host` the client used |
| `X-Forwarded-Port` | The port of that `Host` (else 80 or 443), not the listener's port, so apps build correct URLs behind port forwarding |
| `Forwarded` | The same facts in RFC 7239 form |
| `X-Request-Id` | Kept if the client sent one, otherwise a random id |

Your app can trust these headers for requests that come through the proxy, which is the only way in from outside the server thanks to the `127.0.0.1` bindings. (Other containers on the private network can still call it directly.) If you put another proxy or a CDN in front of Ferry, `X-Forwarded-For` is that proxy's address; CDN-specific headers such as `CF-Connecting-IP` are passed through untouched for apps that opt into them.

## Timeouts and limits

Every client connection to the proxy is bounded:

| Limit | Value |
|---|---|
| Open connections | Derived from the process's open-file limit, at most 10,000. `ferryd` raises its soft open-file limit to the hard limit at startup. |
| Connections per client address | 256 (an IPv6 client counts per /64). Loopback clients, such as a local front proxy or tunnel, are exempt. |
| TLS handshake | 10 seconds |
| First request head, and each next head on HTTP/1 | 30 seconds (this also bounds idle HTTP/1 keep-alive) |
| Idle connection (no request in flight) | 60 seconds, 5 seconds while the connection limit is reached |
| Pause while sending a request body | 60 seconds, then `408` |

Requests in flight (streamed responses such as Server-Sent Events, long downloads, uploads that keep sending) and websocket tunnels are never cut by these timeouts. On the API side, request bodies are limited to 2 MiB, source uploads to 512 MiB and GitHub deliveries to 25 MiB.

## One server per data directory and prefix

Two safety rules keep a server from ever touching another one's workloads. Without them, a second `ferryd` would see the first one's containers as orphans and remove them.

- **One process per data directory.** `ferryd` holds an exclusive lock on `<data-dir>/ferryd.lock` while it runs. A second one fails with `another ferryd is already running with data directory …`.
- **One data directory per Docker name prefix.** `ferryd` records which data directory owns its prefix (`--name-prefix`, default `ferry`) on a marker volume `<prefix>-owner`, labelled with the `instance_id` and the data directory's path. It refuses to start when the prefix belongs to another data directory, or when a fresh data directory finds containers with its prefix it doesn't know:

```text title="ferryd" noCopy
Error: Docker resources with prefix 'ferry' belong to another Ferry server (data dir /var/lib/ferry). Run this server with a different --name-prefix, stop the other server, or pass --take-over to adopt the resources (the other server's containers will then be managed — and possibly removed — by this one).
```

To run several servers on one Docker daemon, give each its own `--name-prefix` and `--data-dir`. A moved data directory keeps its `instance_id`, so it starts again with the same `--name-prefix` and no extra flag. `--take-over` is only for a data directory that lost its `instance_id` (for example, you restored only `ferry.db`), and never while another server uses the prefix: the server that takes over removes the other server's containers as orphans. Inside a server, the engine only lists and touches containers labelled `ferry.instance=<prefix>`. See [Multiple servers](/docs/guides/multiple-servers).

## Shutdown

The first `SIGINT` or `SIGTERM` starts a graceful shutdown: the API stops accepting requests and gets up to 10 seconds to finish those in flight, the proxy drains, and the engine stops job runs and records interrupted deploys (up to 25 seconds). Containers keep running: the next start picks them up. A second signal exits at once (exit code 130).

## One misbehaving service

Anyone who can deploy can run any code on the server, so Ferry can't stop a hostile app. It does keep a buggy or runaway one from taking the server down: every container it starts (service instances, one-off jobs, cron runs and datastores; not builds) runs with a memory limit, a CPU limit, a process limit and log rotation. With the default server options:

| When a service… | What happens |
|---|---|
| Leaks memory | The kernel kills its container at its memory limit (512 MiB by default, no swap beyond it) instead of picking some other process on the host, such as `ferryd`, `dockerd` or a database. Docker restarts it, `ferryd` logs the kill in the server log, and `ferry status` and the dashboard mark the instance as OOM killed while it restarts. |
| Spins the CPU | It is throttled at its CPU limit (1 CPU per container by default), and the other cores stay free. On a 1-CPU host the default is the whole host: lower `--default-cpu-limit` there. |
| Forks without end | It stops at 1024 processes and threads per container: `fork` fails inside the container, and the host's process table is untouched. |
| Logs without end | Docker's `json-file` log rotates at 10 MiB × 3 files, at most about 30 MiB per container. A Docker daemon configured with another log driver keeps it, with that driver's own limits. |
| Deploys onto a nearly full disk | The deploy, or a new datastore, fails before building or pulling, with a message naming the path. Restarts and rollbacks still work. |

The limits are caps, not reservations: nothing checks that their sum fits the host. When the host itself runs out of memory, the kernel's OOM killer picks a victim among all processes. On Linux, `ferryd` lowers its own score at startup (`--oom-score-adj`, default `-500`) so that containers go first, and never raises a lower value set by its service manager, such as systemd's `OOMScoreAdjust=`. Lowering it needs root or `CAP_SYS_RESOURCE`; without them, `ferryd` logs a warning that suggests `OOMScoreAdjust=` in its systemd unit. The processes `ferryd` starts (`git`, the `docker` CLI) are reset to 0, so a runaway `git` isn't spared at the expense of the apps and databases, and containers never inherit the score, since Docker starts them. See [Resource limits](/docs/concepts/resource-limits) for how the limits work, and [Production setup](/docs/guides/production#size-the-container-limits) for sizing them.

Still **not** contained:

- **Builds.** `docker build` runs in BuildKit, which has no per-build memory or CPU limit: a build can still use all of the host's memory and CPU. Only `--build-concurrency` (default 2) bounds builds, and the free-disk check runs before a build, not during it.
- **Disks.** Volumes (datastores, service disks), containers' own filesystems, images and the build cache have no quotas: a service writing to its disk or its container's filesystem can fill the host's disk. The [free-disk check](/docs/guides/production#the-free-disk-check) only stops new deploys and new datastores; `--keep-images` bounds Ferry's own images, and pruning the rest (`docker image prune`, `docker builder prune`) is up to you.
- **Disk and network I/O.** There are no I/O or bandwidth limits.
- **The private network.** Every service and datastore shares one private network ([networking model](/docs/architecture/networking-model#the-private-network)): any container can reach every service and datastore by name, and datastores are protected by their passwords only.
- **Guards turned off.** A limit of `0` (`--default-memory-limit 0`, `--default-cpu-limit 0`, `--pids-limit 0`, `--log-max-size 0`, `--min-free-disk 0`) turns that guard off.

## Known limitations

- One administrator account: no other users, teams, roles or audit log. Every API token has the same access.
- Secrets are stored unencrypted in `ferry.db` (see [above](#the-data-directory)).
- No IP allow lists, and no rate limiting beyond the connection limits above and the server-wide limit on failed sign-ins.
- Builds have no memory or CPU limit, disks have no quotas, disk and network I/O aren't limited, and every container can reach every service and datastore on the private network (see [One misbehaving service](#one-misbehaving-service)).
- Images must be pullable anonymously: private registry credentials are not supported.
