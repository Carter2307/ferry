The build gets the <Term id="env-var">environment variables</Term> of the service and of its <Term id="env-group">env groups</Term>. See [Environment & env groups](/docs/concepts/environment).

Two examples of use: an install step reads the token of a private registry, and a build puts a public API URL into the code.

## What the build does not get

| Not in the build | The log says |
|---|---|
| The <Term id="injected-variable">variables that Ferry adds</Term> when the app runs (`PORT`, `FERRY_…`) | Nothing |
| A `${{…}}` <Term id="reference" /> that Ferry cannot replace, for example to a service with no deploy | `==> Warning: not available at build time (unresolved references): …` |
| A reserved name, or a name that is not a correct variable name | `==> Not available at build time (reserved or invalid names): …` |

## How to use a variable

The variables come as <Term id="build-secret">build secrets</Term>. See [Secrets in a build](/docs/concepts/builds/build-secrets).

<Accordions>
  <Accordion title="The reserved names">
    Ferry never gives these names to a build. Thus they cannot break the build.

    - `PATH`, `HOME`, `PWD`, `OLDPWD`, `HOSTNAME`, `SHELL`, `USER`, `LOGNAME`, `TERM`, `SHLVL`, `TMPDIR`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `SSH_AUTH_SOCK`.
    - Names that start with `DOCKER_`, `BUILDKIT_`, `BUILDX_`, `COMPOSE_`, `XDG_` or `FERRY_BUILD_`.
  </Accordion>
</Accordions>
