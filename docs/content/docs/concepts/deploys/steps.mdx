The lines that start with `==>` come from Ferry.

## If a step fails

Ferry removes the new instances. The deploy gets the status `build_failed` or `deploy_failed`.

Ferry does not touch the old instances. Your service stays online.

<Callout type="warning" title="A service with a disk stops during a deploy">
A service with a <Term id="disk" /> has one instance. Ferry stops the old instance before it starts the new instance. Thus the service is offline for a short time. See [Disks, scaling & suspend](/docs/concepts/scaling).
</Callout>

<Accordions>
  <Accordion title="Details of each step">
    - **Queue.** Different services deploy at the same time. A new deploy cancels the older deploys of the same service that are in the queue. The server builds 2 images at a time (`--build-concurrency`). The log tells you when a deploy waits for a build slot.
    - **Build.** The name of the image is `<prefix>/<service>:<deploy-id>`. A restart or a rollback uses an image that exists. Before a build, the server must have 1 GiB of free disk space (`--min-free-disk`). The deploy of a cron job stops after this step: it is live, and the schedule uses the new image.
    - **Start.** Ferry chooses the [port](/docs/concepts/deploys/ports), replaces the `${{…}}` references and applies the [memory and CPU limits](/docs/concepts/resource-limits).
    - **Health check.** Ferry copies the output of the new instances into the deploy log.
    - **Switch.** The previous live deploy becomes `deactivated`.
    - **Drain.** For web services and static sites, Ferry first waits 2 seconds for the requests in progress. Then each old instance has 10 seconds to stop.
  </Accordion>
  <Accordion title="Causes of a failure">
    - The build fails.
    - An instance crashes.
    - An instance uses too much memory. The error is `instance ab12cd ran out of memory (limit 512 MiB) — raise the service's memory limit`.
    - The health check gets no good answer before the timeout.
  </Accordion>

  </Accordion>
</Accordions>
