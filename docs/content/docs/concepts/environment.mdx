Each service has its own environment variables. You can also put shared variables in **env groups** and link them to several services, and a value can **reference** a datastore or another service with `${{…}}`: Ferry fills in the real value when the service starts.

## Set variables

<Tabs items={['CLI', 'API']} groupId="interface" persist>
<Tab value="CLI">

```bash title="Terminal"
ferry env set api LOG_LEVEL=info 'DATABASE_URL=${{datastore.app-db.connectionString}}'
ferry env unset api LOG_LEVEL
ferry env api                    # the service's own variables
ferry env ls api --effective     # merged with its env groups
```

`ferry env set` and `ferry env unset` restart the service so the change takes effect; add `--no-restart` to only save, or `--follow` to stream the restart. You can also pass variables when you create or upload a service: `ferry create api -e KEY=VALUE` or `ferry up -e KEY=VALUE`.

Quote values that contain `${{…}}` in single quotes, so your shell leaves them alone.

</Tab>
<Tab value="API">

```bash title="Terminal"
curl -X PATCH 'http://127.0.0.1:7878/api/v1/services/api/env?restart=true' \
  -H "Authorization: Bearer $FERRY_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"set": [{"key": "LOG_LEVEL", "value": "info"}], "unset": ["DEBUG"]}'
```

`PATCH` upserts `set` and removes `unset`; `PUT` with `{"vars": […]}` replaces all of the service's own variables. Both return the service's variables. Without `?restart=true`, nothing restarts. See [Environment variables](/docs/reference/api/env) in the API reference.

</Tab>
</Tabs>

In the dashboard, a service's **Environment** page edits the same variables, with **Save only** and **Save & restart** buttons.

### Limits

| What | Rule |
|---|---|
| Key | Not empty, at most 256 characters, no `=`, whitespace or NUL byte. Each key once per service or group. |
| Value | At most 32 KiB, no NUL byte. |
| Total | Keys plus values of one service or env group at most 256 KiB, and the same limit for a service's merged environment (its groups plus its own variables). |

Ferry has no secret files: every setting is an environment variable.

## When changes apply

Ferry freezes a deploy's environment when the deploy starts its instances. Everything that later starts containers for that deploy uses this snapshot: crash replacements, [scaling](/docs/concepts/scaling), resuming, and [jobs](/docs/concepts/jobs). So a saved change only takes effect with the next deploy or restart.

A restart is a new deploy that reuses the live image with the current settings and environment. It rolls out like any deploy: new instances start and pass their health check before the old ones stop. If it fails, for example because a reference doesn't resolve, the previous deploy keeps serving.

`ferry env set` and `unset` (and the API with `restart=true`) restart the service only when its merged environment really changed, and only if it has something to restart:

| Service state | What happens after a change |
|---|---|
| Live | A restart is queued (trigger `env_change`). |
| A deploy in progress | The restart is queued behind it, so the new values aren't lost. |
| Never deployed | Nothing restarts; its first deploy uses the new values. |
| Suspended | Nothing restarts. After `ferry resume`, run `ferry restart NAME` to apply the change. |

```text title="Terminal"
$ ferry env set api 'X=${{datastore.nope.host}}'
warning: X: reference to unknown datastore 'nope'; deploys fail until it resolves
…
Saved. Restarting 'api' with the new environment.
$ ferry deploys api
ID                         STATUS          TRIGGER      COMMIT   CREATED   DURATION
dep-10a070fcab46468a84e8   deploy_failed   env_change   -        8s ago    0s
dep-cff0ad1231bc4c74b9d5   live            create       -        27s ago   5s
```

## Env groups

An env group is a named set of variables that you link to services. Group names have 1 to 64 letters, digits, `-`, `_` or `.`.

```bash title="Terminal"
ferry env-group create shared LOG_LEVEL=info REGION=eu
ferry env-group link api shared        # prints: Restart to apply: ferry restart api
ferry env-group set shared REGION=us   # restarts the linked live services
ferry env-group show shared            # variables and linked services
ferry env-group unlink api shared
ferry env-group rm shared
```

- **Linking and unlinking don't restart anything.** The group's variables apply from the service's next deploy or restart.
- **Changing a group's variables** (`set`, `unset`) restarts every linked live service whose merged environment changed, unless you pass `--no-restart`.
- **Deleting a group** that is still linked is refused. `--force` deletes it anyway (linked services lose its variables at their next restart), and `--force --restart` restarts them right away.

### Precedence

A service's environment is merged in this order, later layers winning:

1. the variables Ferry [injects](#injected-variables) (`PORT`, `FERRY_*`);
2. its env groups, in the order they were linked;
3. its own variables.

```text title="ferry env ls echo --effective"
LOG_LEVEL=warn
REGION=eu
DATABASE_URL=${{datastore.app-db.connectionString}}
Merged from env group(s) shared, extra, then 'echo''s own variables (which win). ${{…}} references are resolved, and PORT/FERRY_* added, at start.
```

Here `shared` sets `LOG_LEVEL=info`, `extra` (linked later) sets `LOG_LEVEL=debug` and the service's own `LOG_LEVEL=warn` wins. Without the service's own value, the service would get `debug`.

## References

A value can embed `${{kind.name.property}}`. Ferry resolves it each time a container starts, so an app always gets the current host, port or password.

```bash title="Terminal"
ferry env set api \
  'DATABASE_URL=${{datastore.app-db.connectionString}}' \
  'REDIS_URL=${{datastore.cache.connectionString}}' \
  'SEARCH_URL=${{service.search.internalUrl}}/v1'
```

**Datastores** (kind `datastore`, or `db` / `database`):

| Property | Aliases | Value |
|---|---|---|
| `connectionString` | `url`, `internalUrl` | URL on the private network, e.g. `postgresql://app_db:…@app-db:5432/app_db` |
| `externalConnectionString` | `externalUrl` | URL through the port published on the server, with the `--advertise-host` host |
| `host` | `hostname` | The datastore name, e.g. `app-db` |
| `port` | | `5432` (Postgres) or `6379` (Redis) |
| `user` | `username` | The Postgres user, or `default` for Redis |
| `password` | | The generated password |
| `database` | `databaseName` | The Postgres database name (Redis has none) |

**Services** (kind `service`, or `svc`):

| Property | Aliases | Value |
|---|---|---|
| `host` | `hostname` | The service name, its hostname on the private network |
| `port` | | The port the service listens on |
| `hostport` | | `host:port`, e.g. `api:3000` |
| `internalUrl` | | `http://host:port` |
| `url` | `externalUrl` | The public URL (web services and static sites only) |

Rules and behaviors:

- A reference that can't be resolved (unknown kind, name or property, or a service without a public URL) fails the deploy or restart with a clear error. The live deploy keeps serving. The CLI checks the syntax before saving and warns about names that don't exist yet.
- `port`, `hostport` and `internalUrl` need the target service's port: it is known once that service has deployed, or when you set its port with `--port`. If the target's first deploy is still running (for example, a blueprint that deploys everything at once), the deploy waits for it, up to 15 minutes or twice the health-check timeout, whichever is longer. Two services that reference each other's port before either has deployed fail right away: deploy one of them without the reference first.
- Deleting a datastore or service that other services reference is refused, and the error lists who uses it. `--force` deletes it anyway; the referencing services then fail at their next deploy or restart.
- References also reach builds: variables are passed to the build with their references resolved. A reference that can't be resolved yet is left out of the build with a warning in the build log.
- To write a literal `${{`, escape it as `$${{`: the value `$${{ not.a.ref }}` reaches the app as `${{ not.a.ref }}`.

The [reference syntax page](/docs/reference/env-references) has the full grammar.

## Injected variables

Ferry adds these variables to every service container. Your own variables with the same names win.

| Variable | Value | Set for |
|---|---|---|
| `PORT` | The port Ferry routes to | Web services, private services, static sites |
| `FERRY` | `true` | All |
| `FERRY_SERVICE_ID` | e.g. `srv-5c57d756f6ad47f59800` | All |
| `FERRY_SERVICE_NAME` | e.g. `echo` | All |
| `FERRY_SERVICE_TYPE` | `web_service`, `private_service`, `background_worker`, `cron_job` or `static_site` | All |
| `FERRY_DEPLOY_ID` | The deploy the container belongs to | All |
| `FERRY_INTERNAL_HOSTNAME` | The service name (its private hostname) | All |
| `FERRY_GIT_COMMIT`, `FERRY_GIT_BRANCH` | The deployed commit and the branch | Deploys from git |
| `FERRY_EXTERNAL_HOSTNAME` | e.g. `echo.localhost` | Web services, static sites |
| `FERRY_EXTERNAL_URL` | e.g. `http://echo.localhost:8080` | Web services, static sites |

Jobs get the same variables except `PORT`. Builds only receive your own variables, not the injected ones; see [Builds & runtimes](/docs/concepts/builds).

## The PORT variable

For services that listen (web services, private services and static sites), Ferry picks the container port once per deploy, in this order:

1. the service's port setting (`--port`, `port:` in a blueprint);
2. a `PORT` variable you set;
3. the build's hint: `80` for static sites served by nginx;
4. the port the image `EXPOSE`s, if it exposes exactly one;
5. the server default, `--default-port` (`10000`).

Ferry injects the result as `PORT` and health-checks and routes to that port. Apps that read `PORT` work with no configuration. If your app listens on a fixed port, set it with `--port`; if you set `PORT` yourself to a value different from the port setting, the deploy log warns you, because the app would listen on the wrong port.
