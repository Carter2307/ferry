A <Term id="cron-job" /> is a service that runs its command on a <Term id="cron-schedule" />.

## Create it

```bash title="Terminal"
ferry create nightly --type cron --image busybox:stable \
  --schedule "0 3 * * *" --start-cmd 'echo "nightly run at $(date)"' --follow
```

```text title="Output (excerpt)" noCopy
==> Pinned busybox:stable as ferry/nightly:dep-4f09d911d31f407fb043
==> Limits: 512 MiB memory, 1 CPU per run
==> Your cron job is live 🎉 (schedule: 0 3 * * *, UTC)
```

A cron job gets its <Term id="image" /> as each other service does: from a repository, from `ferry up`, or from `--image`. But its deploy starts no container. The deploy only saves the image, the variables, the command and the [limits](/docs/concepts/resource-limits) for the runs.

The <Term id="start-command" /> is the command of each <Term id="job-run" />. With no start command, a run uses the default command of the image.

## Run it now

```bash title="Terminal"
ferry run nightly --follow                       # trigger the cron job now
```

On a cron job, `ferry run` runs the command of the cron job. You give no command.

<Accordions>
  <Accordion title="What a cron job does not have">
    A cron job has no instances, no port, no health check, no custom domain and no disk. You cannot scale it.
  </Accordion>
  <Accordion title="Change the command">
    A run uses the command that the last deploy saved. When you change the start command (`ferry update nightly --start-cmd …`), Ferry restarts the cron job automatically. Then the next run uses the new command.

    A change of variables applies as for each other service. See [Environment](/docs/concepts/environment).
  </Accordion>
</Accordions>
