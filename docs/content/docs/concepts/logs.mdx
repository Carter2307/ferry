Ferry keeps three kinds of logs, and streams all of them live over Server-Sent Events (SSE):

| Log | What it holds | Stored | CLI |
|---|---|---|---|
| Deploy log | The build output and Ferry's deploy steps for one deploy | `<data-dir>/logs/deploys/<deploy id>.log`, until the service is deleted | `ferry logs --deploy ID` |
| Runtime log | What the service's containers write to stdout and stderr | By Docker, as long as the containers exist (rotated at 10 MiB × 3 files per container by default) | `ferry logs NAME` |
| Job log | The output of one job run | `<data-dir>/logs/jobs/<job id>.log`, for the newest 100 runs per service | `ferry logs --job ID` |

Every line has a timestamp, a stream (`stdout`, `stderr` or `system`) and, in runtime logs, the instance it came from. Ferry's own messages are `system` lines that start with `==> `.

## Deploy logs

A deploy log starts when the deploy is queued and ends when it is live, failed or canceled.

```bash title="Terminal"
ferry deploy api --follow              # trigger a deploy and stream its log
ferry logs --deploy dep-285c0c8495fe459db551 -f
ferry logs --deploy dep-285c0c8495fe459db551 > deploy.log   # the stored log
```

```text title="Deploy log (excerpt)"
09:38:30 ==> Build successful 🎉
09:38:31 ==> Using port 8000 (EXPOSEd by the image)
09:38:31 ==> Limits: 512 MiB memory, 1 CPU per instance
09:38:31 ==> Starting 1 instance(s)
09:38:31 ==> Started instance 2fa90d (port 8000, published on 127.0.0.1:63012)
09:38:31 ==> Waiting for 1 instance(s) to become healthy: GET /healthz must answer with a status below 400 (timeout 120s)
09:38:31 [2fa90d] docker-echo listening on :8000
09:38:32 ==> Health check passed
09:38:32 ==> Routing traffic to the new instance(s)
09:38:32 ==> Your service is live 🎉
09:38:32 ==> Available at http://echo.localhost:8080
```

While the new instances start, their output is copied into the deploy log (the `[2fa90d]` line above). If an instance crashes during the health check, its last 50 lines are copied in, so you can see why without looking elsewhere. `--follow` exits with code 1 when the deploy fails.

## Runtime logs

```bash title="Terminal"
ferry logs api                # everything the current containers have written
ferry logs api -n 100         # the last 100 lines of each instance
ferry logs api -f             # follow new lines
```

```text title="ferry logs echo -n 2"
09:41:26 [0b4e81] 172.21.0.4 - - [27/Sep/2026 07:41:26] "GET / HTTP/1.1" 200 -
09:41:31 [0b4e81] 172.21.0.4 - - [27/Sep/2026 07:41:31] "GET / HTTP/1.1" 200 -
```

- The output of all instances of the live deploy is merged by timestamp. The instance id in brackets is the end of the container name. Before anything is live, the logs of whatever containers exist are shown.
- `-f` keeps following across redeploys, scaling and crash replacements: new containers are picked up as they appear, and the CLI reconnects if the stream drops.
- When nothing is running, the CLI says why (never deployed, suspended, a deploy in progress, the last deploy failed) and where to look instead.

<Callout type="warning" title="Runtime logs aren't kept">
Runtime logs are read from Docker. When a deploy replaces the containers, or a crashed container is removed, their logs go with them. Docker also rotates each container's log (10 MiB × 3 files by default, see [Processes and logs](/docs/concepts/resource-limits#processes-and-logs)), so the oldest lines of a chatty app are dropped first. Send logs you need to keep to an external log service from your app.
</Callout>

Cron jobs have no runtime logs: each run has its own [job log](#job-logs).

## Job logs

Every [job run](/docs/concepts/jobs), scheduled or one-off, has its own log:

```bash title="Terminal"
ferry jobs nightly                                # find the run
ferry logs --job job-48dd0201159b41c3bb58 -f
ferry run api --follow -- npm run migrate         # start a job and stream it
```

Ferry keeps the logs of the newest finished runs of each service (100 by default, `ferryd --keep-job-runs`) and deletes older ones with their runs.

## Stream logs over the API

The log endpoints answer with `Content-Type: text/event-stream`:

| Endpoint | Query | Ends |
|---|---|---|
| `GET /api/v1/deploys/{deploy_id}/logs` | `follow=true` to keep streaming while the deploy runs | when the deploy is finished (or at once without `follow`) |
| `GET /api/v1/jobs/{job_id}/logs` | `follow=true` | when the run is finished (or at once without `follow`) |
| `GET /api/v1/services/{id}/logs` | `follow=true`, `tail=N` lines per instance | at once without `follow`; with `follow`, when you disconnect |

Each line is an `event: log` whose `data` is a JSON object. A finite stream ends with `event: end` and an empty `data:` field. While a stream is idle, a `: keep-alive` comment is sent every 15 seconds. All streams close when the server shuts down.

```text title="curl -N 'http://127.0.0.1:7878/api/v1/jobs/job-48dd…/logs?access_token=…'"
event: log
data: {"ts":"2026-09-27T07:46:59.504869Z","stream":"system","line":"==> Running `npm run migrate`"}

event: log
data: {"ts":"2026-09-27T07:46:59.634761796Z","stream":"stdout","line":"> node migrate.js"}

event: end
data: 
```

| Field | Type | Description |
|---|---|---|
| `ts` | RFC 3339 timestamp | When the line was written |
| `stream` | `stdout`, `stderr` or `system` | Where it came from; `system` lines are Ferry's |
| `instance` | string, runtime logs only | The instance (last 6 characters of the container name) |
| `line` | string | The text, without the newline |

Like every `/api/v1` request, streams need an API token (the dashboard uses its session instead). Browsers' `EventSource` can't send an `Authorization` header, so `GET` requests also accept the token as `?access_token=`. Prefer the header wherever you can: a token in a URL can end up in logs and browser history.

## The change feed

`GET /api/v1/events` is one SSE stream that reports every change on the server: services, deploys, datastores, env groups and job runs, whether the change came from the API, a webhook or the engine itself (deploy progress, datastore provisioning, cron runs). The dashboard uses it to stay up to date. You can use it for your own automation.

```bash title="Terminal"
curl -N http://127.0.0.1:7878/api/v1/events -H "Authorization: Bearer $FERRY_TOKEN"
```

```text title="Output"
event: ready
data: {}

event: change
data: {"kind":"service","id":"srv-6da2006dc52b4c6ca25f","service_id":"srv-6da2006dc52b4c6ca25f","action":"updated"}

event: change
data: {"kind":"deploy","id":"dep-0d89a8b1d3ab43dc997f","service_id":"srv-7e321e187891447bb187","action":"created"}
```

- `ready` arrives once the feed is watching. Fetch your data after it: every later change is reported.
- `change` events say what changed, not how: `kind` is `service`, `deploy`, `datastore`, `env_group` or `job`; `action` is `created`, `updated` or `deleted`; `service_id` is set for services, deploys and jobs. Fetch the resource to get its new state.
- A client that falls too far behind gets `{"kind":"all","id":"*","service_id":null,"action":"resync"}`: refetch everything.
- The server compares its database every second while someone listens, and right after each API or webhook write, so changes arrive within about a second.

See [Change feed (SSE)](/docs/reference/api/events) in the API reference.

## Metrics and instance status

`ferry status NAME` (or `GET /api/v1/services/{id}/status`) shows each instance's state, port, CPU and memory use against its [limits](/docs/concepts/resource-limits), restart count and start time, read from Docker when you ask. Ferry doesn't keep a history of metrics.

```text title="ferry status api" noCopy
api: degraded — 1/2 instance(s) running
INSTANCE   DEPLOY     STATE                                    PORT    CPU              MEMORY                  RESTARTS   STARTED
3f2a1c     7d0e52aa   running                                  63012   2.1% / 0.5 CPU   301.4 MiB / 512.0 MiB   0          12m ago
9b4e07     7d0e52aa   restarting (OOM killed, exit code 137)   -       -                -                       3          -
note: instance 9b4e07 was killed for running out of memory (limit 512 MiB). Raise the limit with 'ferry update api --memory <SIZE>', then 'ferry restart api'.
```

- **CPU** is the use in percent of one core, then the instance's CPU limit. **MEMORY** is the use, then the memory limit. An unlimited container shows the use alone.
- **STATE** is Docker's state. For an instance that isn't running, it adds why it stopped: its exit code (`exited (exit code 1)`), or `OOM killed` when the kernel killed it for going over its memory limit. The `note:` line, printed on standard error, says how to raise the limit.
- On the dashboard, the service's **Overview** shows the same per instance, with an **OOM killed** badge.

The API returns these fields for each instance, among others (see [Runtime status](/docs/reference/api/services#runtime-status)):

| Field | Type | Description |
|---|---|---|
| `cpu_percent` | number or `null` | CPU use, in percent of one core; `null` when unknown, for example for a stopped container |
| `memory_bytes` | integer or `null` | Memory use; `null` when unknown |
| `cpu_limit` | number or `null` | The container's CPU limit, in CPUs; `null` when unlimited |
| `memory_limit_bytes` | integer or `null` | The container's memory limit; `null` when unlimited |
| `oom_killed` | boolean | The kernel killed the container's process for going over its memory limit, the last time it exited |
| `exit_code` | integer or `null` | The exit code of the last exit, for exited and restarting containers |

Docker clears the out-of-memory flag as soon as the container runs again, so `oom_killed` is only `true` while an instance is restarting or stopped. Past kills are in the [server log](#server-logs).

## Server logs

`ferryd` writes its own log (lifecycle events, proxy warnings, certificate requests) to standard output at the `info` level. Set the `RUST_LOG` environment variable to change it, for example `RUST_LOG=debug ferryd` to also log every proxied request. Under systemd, read it with `journalctl -u ferryd`.

Every deploy that fails is logged as a warning that names the service and says as much as the end of its deploy log: the error, and the hint when Ferry has one.

```text title="journalctl -u ferryd" noCopy
WARN deploy failed: instance 2e58a7 exited with code 0: its command `node ./dist/index.js` ended without an error, but a web service must keep running and listen on port 10000 service=libui deploy=dep-1edd534d254f47bbbde5 status=deploy_failed hint=the service has no start command, so Ferry picked this one from the project (…)
```

What the app itself printed is not copied there: it stays in the deploy log (`ferry logs --deploy ID`).

The server log is also where out-of-memory kills end up: `ferryd` logs a warning for every container of the server the kernel kills, for example `instance a1b2c3 of service 'api' ran out of memory (limit 512 MiB) — raise the service's memory limit`. At startup, it warns about [limits](/docs/concepts/resource-limits#cpu-limits-and-the-host) the Docker host can't enforce.
