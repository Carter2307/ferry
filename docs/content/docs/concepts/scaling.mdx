These operations change what runs without building anything new. Scaling, suspending and resuming start or stop containers from the **live deploy**. Restarting rolls out the live image again with the current settings.

| Operation | Command | New deploy? | Downtime |
|---|---|---|---|
| Scale | `ferry scale NAME N` | no | none |
| Suspend | `ferry suspend NAME` | no | yes: the proxy answers `503` |
| Resume | `ferry resume NAME` | no | until the instances accept connections |
| Restart | `ferry restart NAME` | yes (trigger `restart`), reusing the live image | none (except for services with a disk) |

## Scale instances

Web services, static sites, private services and background workers run 1 instance by default, and up to 50.

<Tabs items={['CLI', 'API']} groupId="interface" persist>
<Tab value="CLI">

```bash title="Terminal"
ferry scale api 3
ferry create api --repo https://github.com/you/api --instances 2   # at creation
ferry status api
```

</Tab>
<Tab value="API">

```bash title="Terminal"
curl -X POST http://127.0.0.1:7878/api/v1/services/api/scale \
  -H "Authorization: Bearer $FERRY_TOKEN" \
```

- Scaling starts or stops containers in place from the live deploy's snapshot: same image, environment and command. Settings or variables you changed since the last deploy don't apply to the new instances.
- New instances receive traffic as soon as they accept connections. Removed instances get a 10-second stop grace period.
- The proxy spreads requests over the instances of a web service or static site, round-robin. On the [private network](/docs/concepts/networking#private-network), the service's name resolves to all of its instances.
- During a deploy, the new count is saved and applied right after the deploy finishes.
- Cron jobs can't be scaled: each run starts its own container. Instances must be at least 1: to stop a service, [suspend](#suspend-and-resume) it.

The service state is `degraded` while fewer instances run than you asked for, for example just after a crash, and `live` again once the [reconciler](/docs/concepts/self-healing) has replaced them.

<Callout type="info" title="Manual scaling only">
Ferry doesn't autoscale, and containers run without CPU or memory limits. `ferry status` shows each instance's CPU and memory use.
</Callout>

## Persistent disks

A service's filesystem is thrown away with its container at every deploy. To keep files, give the service a disk: a Docker volume mounted at a path you choose.

```bash title="Terminal"
ferry create files --repo https://github.com/you/files --disk /data
ferry update api --disk /var/lib/api     # add or move the disk (next deploy)
ferry update api --disk ""               # stop mounting it (next deploy)
```

In a blueprint, `disk: { mountPath: /data }` does the same; `name` and `sizeGB` are accepted and ignored.

- **Volume:** `<prefix>-svc-<service id>-disk`, created on first use. It keeps its data across deploys, restarts and server restarts.
- **Where:** web services, private services and background workers. Not static sites or cron jobs. The mount path must be absolute and not `/`.
- **One instance:** a service with a disk runs exactly 1 instance; scaling it higher is refused.
- **Deploys stop the old instance first.** Two containers must not write to the disk at once, so deploys and restarts of a disk service stop the old instance (10-second grace period), then start the new one. The service is unavailable for that short time:

  ```text title="Deploy log"
  ==> Mounting disk at /data
  ==> Stopping 1 old instance(s) first (services with a disk are redeployed in place)
  ==> Starting 1 instance(s)
  ```

- **One-off jobs** on the service mount the same disk. See [Disk access](/docs/concepts/jobs#disk-access).
- **Size:** Ferry doesn't limit a disk's size. It uses the server's Docker storage.
- **Deletion:** the volume is deleted with the service. Removing the disk setting only stops mounting it.

<Callout type="warning" title="Back up disks yourself">
Ferry doesn't snapshot or back up disks. See [Production setup](/docs/guides/production#back-up-your-data) for a backup approach.
</Callout>

## Suspend and resume

```bash title="Terminal"
ferry suspend api
# Suspended 'api' (state: suspended)
ferry resume api
```

**Suspend** stops a service without deleting anything:

1. the proxy answers `503` with `x-ferry-error: suspended` right away;
2. queued and running deploys are canceled, and running jobs are stopped;
3. every instance is stopped and removed.

Settings, variables, deploys and disk data stay. While a service is suspended, cron schedules don't fire, GitHub pushes and blueprints don't deploy it, the deploy hook answers `409`, and `ferry deploy` is refused: resume it first.

**Resume** starts the live deploy's instances again, without a new deploy or build. They get traffic as soon as they accept connections. If the live deploy's image has been deleted meanwhile, resume is refused; a manual deploy (`ferry deploy NAME` or `ferry up`) then deploys the service and resumes it once live.

## Restart

```bash title="Terminal"
ferry restart api --follow
```

A restart is a new deploy (trigger `restart`) that reuses the live deploy's image with the service's **current** settings and environment. It's how saved changes to variables, env group links or settings reach a running service without rebuilding. It rolls out like any deploy: health check, then switch, then the old instances stop. `ferry env set` and `ferry env-group set` restart for you.

The service must have a live deploy. See [Deploys](/docs/concepts/deploys) for rollbacks, cancels and deploy states.
