Ferry is a Rust workspace with two front-end projects next to it: the web dashboard in `web/` and this documentation site in `docs/`. The Rust build never runs Node: it embeds the dashboard only if it was built first.

## Requirements

| Tool | Version | Needed for |
|---|---|---|
| Rust | 1.89 or newer (edition 2024) | `ferryd`, `ferry` and every crate |
| Docker | Docker Desktop on macOS works | Running `ferryd` and the end-to-end tests |
| `git` and `docker` CLIs | on the `PATH` | Builds: `ferry-build` runs them |
| Node.js | 20.19 or newer, with npm | The dashboard (`web/`) and the docs (`docs/`) |

Each crate has unit tests next to its code and integration tests in `crates/<crate>/tests/`. [Architecture](/docs/architecture/overview) explains what each crate does and how they depend on each other. Read `DESIGN.md` before changing behavior: it is the contract the crates are written against.

## Build and run

<Steps>
<Step>

### Build the dashboard (optional)

```bash title="Terminal"
cd web && npm ci && npm run build && cd ..
```

`ferry-api` embeds `web/dist` when it compiles. Without it, the server still works, and `/` shows a page explaining how to build the dashboard. To work on the dashboard itself, see [Web client](/docs/contributing/web-client).

</Step>
<Step>

### Build and start the server

```bash title="Terminal"
cargo build
./target/debug/ferryd run --data-dir ./ferry-data
```

`ferryd run` keeps the server in the foreground, so its log is in front of you and <kbd>Ctrl</kbd>+<kbd>C</kbd> stops it; without `run`, `ferryd` starts in the background and logs to `ferry-data/ferryd.log` (`ferryd logs -f`). It prints the API URL and, while the server has no account, the `Create your account` link: open it once to create the account the dashboard signs in with. The server token for the commands below is in `ferry-data/api_token`. `./ferry-data` is the default and is ignored by git. Set `RUST_LOG=debug` (or a filter such as `RUST_LOG=ferry_engine=debug`) for more detail; the default level is `info`.

<Callout type="tip" title="Keep experiments away from your real server">
If a Ferry server already runs on this machine, give your development server its own data directory, name prefix and ports: `--data-dir ./dev-data --name-prefix ferrydev --api-addr 127.0.0.1:17878 --proxy-addr 127.0.0.1:18080`. `ferryd` refuses to start on a prefix another data directory owns, which protects the other server's containers.
</Callout>

</Step>
<Step>

### Deploy something

```bash title="Terminal"
export FERRY_SERVER=http://127.0.0.1:7878
export FERRY_TOKEN="$(cat ferry-data/api_token)"
cd examples/node-hello
../../target/debug/ferry up --follow
curl http://node-hello.localhost:8080
```

`FERRY_SERVER` and `FERRY_TOKEN` point the CLI at the development server without overwriting the config that `ferry login` saved for your usual server. The server token works without an account and without approving a login in the dashboard. `cargo run -p ferry-cli -- <args>` works too.

</Step>
</Steps>

For release builds, use `cargo build --release`: the binaries land in `target/release/`.

## Branches and commits

- **New features start from `dev`.** Create a branch from an up-to-date `dev`, named after the change, and merge it back into `dev`:

  ```bash title="Terminal"
  git switch dev && git pull
  git switch -c feat/my-feature
  ```

- **Commit messages** start with the area they touch, then a short summary: `ferry-api: SSE change feed, embedded web client, job cancel`, `web: blue primary color`, `ferry-engine: fix verified findings`. Use the crate name, `web` or `docs`. The body lists the changes as bullets when there are several.
- **Keep generated files in sync.** A change to a CLI command, a `ferryd` flag, an API route or a DTO changes the generated reference pages: run `npm run generate` in `docs/` and commit the result (see [Docs site](/docs/contributing/docs-site)).
- **Update `DESIGN.md`** in the same change when you change a contract between crates, an API route or a documented behavior.

## Coding rules

These come from `DESIGN.md` §15 and apply to every crate:

- **Rust 2024, stable toolchain.** No `unwrap()` or `expect()` outside tests, except on invariants explained in a comment. No `todo!()` left behind.
- **Errors** are `ferry_core::Error`, with context in the message (`pulling image nginx: …`). The variant decides the HTTP status (`Invalid` → 400, `NotFound` → 404, `Conflict` → 409, `Docker` → 502…).
- **Logging** uses `tracing`: `info` for lifecycle events, `debug` for detail. Never log secrets.
- **Blocking work** (tar, heavy filesystem work) runs in `spawn_blocking`.
- **Public signatures** in `crates/*/src/lib.rs` are the contract between crates: change them deliberately, and say so in the change. Private modules are free to reorganize.
- **Dependencies** go into the crate's own `Cargo.toml` with an explicit version, not into the workspace root. Crates must not depend on each other beyond the [dependency graph](/docs/architecture/overview#crates).
- **Formatting and lints:** `cargo fmt` (the repository's `rustfmt.toml` sets a 120-column width) and `cargo clippy --workspace --all-targets -- -D warnings` must pass.

Then run the tests: [Testing](/docs/contributing/testing).
