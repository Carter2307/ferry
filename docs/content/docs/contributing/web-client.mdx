The dashboard is a single-page app in `web/`, with its own toolchain. `ferryd` serves it at `/`, but the Rust build never runs Node: `ferry-api` embeds whatever `web/dist` holds when it compiles.

| | |
|---|---|
| UI | React 19, TypeScript (strict), shadcn/ui (Radix primitives, customized in `src/components/ui`), lucide icons |
| Styling | Tailwind CSS v4, the Ferry design tokens in `src/styles/tokens.css`, light and dark themes |
| Server state | TanStack Query v5 (`src/lib/api/queries/*`) |
| Client state | Zustand (`src/stores/auth.ts`, `src/stores/ui.ts`) |
| Routing | React Router v7 with history URLs and code-split pages |
| Build and tests | Vite, Vitest |

## Development loop

<Steps>
<Step>

### Start a server

Run `ferryd` as in [Development setup](/docs/contributing/development#build-and-run). The dev server only needs its API; its embedded dashboard doesn't matter.

</Step>
<Step>

### Start Vite

```bash title="Terminal"
cd web
npm install
FERRY_API_URL=http://127.0.0.1:7878 npm run dev    # → http://localhost:5173
```

Vite serves the app with hot module replacement and proxies `/api`, `/hooks` and `/healthz` to `FERRY_API_URL` (default `http://127.0.0.1:7878`). The proxy forwards the host the browser used (`X-Forwarded-Host`), which `ferryd` compares with the `Origin` of requests that carry the session cookie. Server-Sent Events (log streams and the change feed) pass through the proxy unbuffered and uncompressed.

</Step>
<Step>

### Sign in

Open `http://localhost:5173` and sign in with the email and password of the server's account. On a server without an account, the app shows **Create your account** instead: take the setup code from the link `ferryd` printed (`ferryd status` prints it again), or from `<data-dir>/setup_code`. In development, `/dev/patterns` shows the dashboard's shared UI patterns on one page.

</Step>
</Steps>

| Script | What it does |
|---|---|
| `npm run dev` | Vite dev server with HMR and the API proxy (port 5173) |
| `npm run build` | `tsc -b && vite build` → `dist/`, with hashed files under `dist/assets/` |
| `npm run preview` | Serves `dist/` with the same proxy (port 4173) |
| `npm test` | Vitest unit tests (`src/**/*.test.ts` and `src/**/*.test.tsx`) |
| `npm run typecheck` | `tsc -b --noEmit` |
| `npm run lint` | ESLint (typescript-eslint, react-hooks, react-refresh) |

## How ferryd serves it

1. `npm run build` writes `web/dist/index.html` and `web/dist/assets/*`.
2. `ferry-api`'s build script embeds every file of `web/dist` into the binary (`FERRY_WEB_DIST` points it at another directory). Without a built client, it embeds a placeholder page that explains how to build one, so the Rust workspace always compiles.
3. `ferryd` serves the app at `/`. Files under `/assets/` get `Cache-Control: public, max-age=31536000, immutable`; everything else, `index.html` first, gets `no-cache` with an ETag. Any other `GET` outside `/api`, `/hooks` and `/healthz` that isn't a file gets `index.html`, so history URLs such as `/services/api/logs` survive a reload. A missing `/assets/` file stays a 404.

To try a production build in a real server without recompiling Rust, point `ferryd` at the directory:

```bash title="Terminal"
cd web && npm run build && cd ..
FERRY_UI_DIR=web/dist ./target/debug/ferryd
```

## Talking to the API

The dashboard only uses the public REST API, like the CLI: see the [API overview](/docs/reference/api-overview).

- **Signing in:** the app first asks `GET /api/v1/auth/status`, which says whether the server still needs its account (`/setup`), or whether this browser is signed in (`/login` otherwise). Signing in sets the session cookie, which is `HttpOnly`: no script can read it, so `src/stores/auth.ts` only knows whether there is a session, and who the account is. The pages are in `src/pages/login/`, with `/cli-login`, the page that approves a `ferry login`.
- **Queries and mutations** are JSON calls to `/api/v1/*` on the same origin (no CORS). The browser sends the session cookie on its own; no `Authorization` header is set. `src/lib/api/client.ts` wraps `fetch` and turns error bodies into `ApiError { status, code, message }`.
- **Push** uses Server-Sent Events read with `fetch()` and a streaming parser (`src/lib/api/sse.ts`), authenticated by the same cookie: the log streams, and the change feed `/api/v1/events`.
- **The change feed** turns each `change` event into TanStack Query invalidations (`src/lib/api/events.ts`). It reconnects with an exponential backoff from 1 to 15 seconds; while it is down (or on an older server without it, which answers 404), queries fall back to polling: 5 seconds for lists, 2 to 3 seconds for the detail on screen.
- **Storage:** no token or secret is kept in `localStorage`: the session is the cookie, which the page can't read. Only UI preferences (theme, rail, log viewer options) are stored, under `ferry.ui`. `public/theme-init.js` applies the saved theme before first paint; it is an external file so the app works under a strict `script-src 'self'` Content Security Policy.

### Adding an endpoint

The TypeScript side mirrors the Rust types by hand. When the API changes:

1. Update `src/lib/api/types.ts`, the mirror of `ferry-core`'s `dto.rs`, `models.rs` and `logs.rs`.
2. Add the call to `src/lib/api/endpoints.ts` and, for new cached data, a key to `src/lib/api/keys.ts`.
3. Add or extend the query and mutation hooks in `src/lib/api/queries/`.
4. For data that should refresh on its own, add its query keys to the invalidations of the matching change `kind` in `src/lib/api/events.ts`.

Then regenerate the API reference of these docs (see [Docs site](/docs/contributing/docs-site#generated-references)).

## Design tokens

Colors, radii and font families live in one file, `web/src/styles/tokens.css`, as plain CSS custom properties: light values on `:root`, dark values on `.dark`. The dashboard imports it from `globals.css` and this docs site imports it too, so both always match.

<Callout type="warning" title="Change colors in tokens.css only">
Both projects depend on it. After a change, run `npm run typecheck`, `npm run build` and `npm test` in `web/`, and `npm run build` in `docs/`.
</Callout>
