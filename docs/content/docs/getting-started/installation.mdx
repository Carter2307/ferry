Ferry is one Rust workspace that builds two binaries:

- **`ferryd`**, the server. One process runs the REST API, the web dashboard, the public reverse proxy and the engine that builds and runs your apps.
- **`ferry`**, the command-line client. It talks to `ferryd` over the REST API.

The web dashboard is a separate React app in `web/`. It is compiled into `ferryd`, so there is nothing else to deploy.

## Requirements

| Tool | Version | Used for |
|---|---|---|
| Docker | Engine 27.3 or newer, or Docker Desktop | Running everything. Builds use the `docker` CLI with BuildKit. |
| git | any recent version | Cloning repositories for git deploys |
| Rust | stable 1.89 or newer (install with [rustup](https://rustup.rs)) | Building `ferryd` and `ferry` |
| Node.js | 20.19 or newer, with npm | Building the web dashboard |

Ferry runs on Linux and macOS. On macOS, Docker Desktop works as is: Ferry never connects to container IPs, only to ports published on `127.0.0.1`.

### How ferryd finds Docker

`ferryd` connects to the Docker daemon named by the `DOCKER_HOST` environment variable, or to `/var/run/docker.sock` when it isn't set. On macOS it also tries Docker Desktop's socket, `~/.docker/run/docker.sock`. Builds run the `docker` CLI against the same daemon.

| `DOCKER_HOST` form | Supported |
|---|---|
| `unix:///path/to/docker.sock` | Yes |
| `tcp://host:port`, `http://host:port` | Yes, plain TCP only |
| TLS (`DOCKER_TLS_VERIFY`, `DOCKER_CERT_PATH`), `ssh://` | No |

The daemon must run on the same machine as `ferryd`, or forward its published ports to it like Docker Desktop, Colima and OrbStack do: Ferry reaches your containers through the ports they publish on `127.0.0.1`.

With Colima, OrbStack or another Docker context, point `ferryd` at that context's socket before you start it:

```bash title="Terminal"
export DOCKER_HOST=$(docker context inspect --format '{{.Endpoints.docker.Host}}')
```

<Callout type="info" title="Why Docker 27.3">
Build-time environment variables reach your build as BuildKit secrets (`RUN --mount=type=secret,…,env=…`), which need Docker Engine 27.3 or newer. With an older engine, builds that use environment variables fail with a message that asks you to upgrade. See [Builds & runtimes](/docs/concepts/builds#build-time-environment).
</Callout>

At run time, Ferry only needs Docker, plus git for services that deploy from a repository. Rust and Node.js are only needed to build it.

## Build from source

<Steps>
<Step>
### Clone the repository

```bash title="Terminal"
git clone https://github.com/Carter2307/ferry
cd ferry
```
</Step>

<Step>
### Build the web dashboard

```bash title="Terminal"
(cd web && npm ci && npm run build)
```

This writes the dashboard to `web/dist`. The Rust build embeds that folder into `ferryd` at compile time, so build the dashboard first.
</Step>

<Step>
### Build the binaries

```bash title="Terminal"
cargo build --release
```

You get `target/release/ferryd` and `target/release/ferry`.
</Step>

<Step>
### Put them on your PATH (optional)

```bash title="Terminal"
sudo install -m 0755 target/release/ferryd target/release/ferry /usr/local/bin/
```

The rest of the docs call them `ferryd` and `ferry`. Without this step, run `./target/release/ferryd` and `./target/release/ferry` instead.
</Step>
</Steps>

<Callout type="tip" title="Skipped the dashboard build?">
`ferryd` still compiles without Node.js. It then serves a placeholder page at `/` that explains how to build the dashboard, and the REST API and the CLI work normally. To use a dashboard you built later without recompiling the server, start `ferryd` with `FERRY_UI_DIR=/path/to/web/dist`.
</Callout>

## Start the server

Run `ferryd`. It needs access to the Docker daemon, so run it as a user that can use Docker.

```bash title="Terminal"
ferryd
```

On first start, `ferryd` creates its data directory. It starts the server in the background, waits until it listens and prints where everything is, then what to do next:

```text title="Output" noCopy
  Ferry 0.1.0 is running in the background (pid 48213)
  Dashboard + API : http://127.0.0.1:7878
  Dashboard (proxy): http://ferry.localhost:8080
  Apps            : http://<name>.localhost:8080
  Docker          : 29.2.0 (8 CPUs, 7.7 GiB)
  Data            : /home/you/ferry-data
  Limits          : 512 MiB / 1 CPU per container (default), 1024 pids, logs rotated at 10 MiB × 3
  Free disk check : deploys need 1 GiB free

  Create your account: http://127.0.0.1:7878/setup?code=5b0e…

  Logs            : ferryd logs -f
  Stop            : ferryd stop
```

The terminal is yours again, and the server keeps running after you close it. If the server can't start (Docker isn't running, a port is taken), `ferryd` prints the error and exits with code 1.

The `Docker` line shows the CPUs and memory of the Docker host (with Docker Desktop, those of its virtual machine). The `Limits` line shows the memory and CPU limits every container gets unless its service or datastore sets its own; see [Resource limits](/docs/concepts/resource-limits).

Check that it answers:

```bash title="Terminal"
curl http://127.0.0.1:7878/healthz
# ok
```

### Create your account

A Ferry server has one administrator account: an email and a password. There are no other users, teams or roles.

While the server has no account, the banner ends with the `Create your account` link. Open it in a browser:

1. The page **Create your account** asks for your email and a password of at least 8 characters. The setup code is already filled in from the link.
2. **Create account** creates the account and signs that browser in to the dashboard.

Creating the account takes the setup code, so only someone who can read the server's terminal or its data directory can do it. The code is also in `<data-dir>/setup_code` (mode `0600`), and `ferryd status` prints the link again. The file is deleted once the account exists.

From then on, the banner ends with this line instead, and you sign in to the dashboard with your email and password:

```text title="Output" noCopy
  Connect the CLI : ferry login
```

When the API isn't at the default `http://127.0.0.1:7878`, the line reads `ferry login --server <url>`. The banner never prints a token.

If you forget the password, run [`ferryd reset-password`](/docs/reference/server-options#ferryd-reset-password) on the server: it asks for a new password twice and signs every browser out.

<Callout type="warning" title="The account controls the whole server">
Whoever signs in can deploy code and read every environment variable on the server. Don't expose the API to the internet without HTTPS. See [Security model](/docs/architecture/security).
</Callout>

### API tokens

The dashboard signs in with the account. The CLI, scripts and CI authenticate with an API token (`fy_` followed by 40 hex characters), sent as `Authorization: Bearer <token>`. There are three ways to get one:

| Token | Where it comes from | Use it for |
|---|---|---|
| A terminal's token | [`ferry login`](/docs/getting-started/cli#log-in) asks for one, and you approve the request in the dashboard | The CLI on your machine |
| A named token | **Server → Account → API tokens** in the [dashboard](/docs/getting-started/dashboard#server): a name, an optional expiry, and the token shown once | CI, scripts and machines without a browser |
| The server token | `<data-dir>/api_token` (mode `0600`), generated on first start and reused by later starts | Scripts on the server itself |

The first two are listed under **Server → Account**, with their last 4 characters and when they were last used, and can be revoked there at once. The server token is never printed, isn't listed in the dashboard and can't be revoked there. To use a server token of your choice, start `ferryd` with `--api-token` or `FERRY_API_TOKEN`: it then takes precedence over the file.

```bash title="Terminal"
# On the server itself, without logging in
export FERRY_TOKEN="$(cat ferry-data/api_token)"
ferry services
```

<Callout type="warning" title="Treat a token like a root password">
An API token can do everything in the API except manage the account, its sessions and its tokens. Don't commit one, and revoke a token you no longer use. See [Security model](/docs/architecture/security#api-tokens).
</Callout>

### The data directory

By default the data directory is `./ferry-data`, relative to where you start `ferryd`. Pass `--data-dir` (or set `FERRY_DATA_DIR`) to put it somewhere stable. `ferryd` creates it with mode `0700`, because it holds environment values, datastore passwords and repository credentials.

| Path | Contents |
|---|---|
| `ferry.db` | SQLite database: services, deploys, variables, env groups, datastores, job runs, the account, its sessions and API tokens |
| `api_token` | The server token, for scripts on the server itself (mode `0600`) |
| `setup_code` | The code that creates the account (mode `0600`); only while the server has no account |
| `instance_id` | Identifies this data directory to Docker (mode `0600`) |
| `ferryd.lock` | Held while `ferryd` runs |
| `ferryd.json` | The running server's process id and addresses, read by `ferryd status` and `ferryd stop`; removed when it stops |
| `ferryd.log` | Output of a server started in the background (`ferryd logs`) |
| `logs/` | Deploy and job logs, one JSON object per line |
| `builds/` | Scratch build contexts, removed after each build |
| `repos/` | Git caches, one per service, for fast incremental fetches |
| `uploads/` | Source archives sent by `ferry up` |
| `certs/` | ACME account and TLS certificates |

Back up the data directory: it is the whole state of the server. Datastore data lives in Docker volumes, not in this directory (see [Datastores](/docs/concepts/datastores)).

### Ports and URLs

| What | Default address | Flag |
|---|---|---|
| API and dashboard | `http://127.0.0.1:7878` | `--api-addr` |
| Public HTTP proxy, where your apps live | `0.0.0.0:8080` | `--proxy-addr` |
| Public HTTPS proxy | off | `--https-addr` with `--acme-email` |

With the defaults:

- **Dashboard:** http://127.0.0.1:7878, or http://ferry.localhost:8080 through the proxy.
- **Your apps:** `http://<name>.localhost:8080`. Browsers resolve every `*.localhost` name to `127.0.0.1`, so there is no DNS to set up on your machine.
- **API reference of your server:** Swagger UI at http://127.0.0.1:7878/api/docs (its **Authorize** button takes an API token) and the OpenAPI 3.1 document at `/api/openapi.json`. Both are served without a token.
- **Liveness probe:** `/healthz` answers `ok`, without a token.

By default the API listens on `127.0.0.1` only. Reach it from another machine over SSH (`ssh -L 7878:127.0.0.1:7878 your-server`) rather than binding it publicly. See [Production setup](/docs/guides/production).

### Background and foreground

`ferryd` without a command picks how to run from where it is started:

- **from a terminal**, it starts the server in the background, like `ferryd start`;
- **anywhere else** (under systemd or launchd, in a container, in a pipe or a script), it runs the server in the foreground, like `ferryd run`. A service manager needs the server to stay in the foreground: write `ferryd run` in unit files, as in [Production setup](/docs/guides/production).

| Command | What it does |
|---|---|
| `ferryd start` | Starts the server in the background and returns once it listens. Takes the same options as `ferryd`. |
| `ferryd run` | Runs the server in the foreground and logs to the terminal, until <kbd>Ctrl</kbd>+<kbd>C</kbd> or `SIGTERM`. Takes the same options as `ferryd`. |
| `ferryd status` | Says whether the server runs and where it listens, and prints the `Create your account` link while there is no account. The exit code is 0 when it runs and 3 when it doesn't. |
| `ferryd logs` | Prints the last 100 lines of the server's log. `-n N` changes the number, and `-f` keeps printing new lines. |
| `ferryd stop` | Shuts the server down and waits until it has stopped. |
| `ferryd reset-password` | Replaces the account's password and signs every browser out. Works while the server runs. |

A server started in the background writes its output to `<data-dir>/ferryd.log`. When that file is larger than 10 MiB, the next `ferryd start` moves it to `ferryd.log.1` and starts a new one. A server in the foreground has no log file: its output goes to the terminal, or to the journal under systemd.

`ferryd stop`, `ferryd status`, `ferryd logs` and `ferryd reset-password` find the server through its data directory. Run them from the directory where you started `ferryd`, or pass the same `--data-dir` (or `FERRY_DATA_DIR`):

```bash title="Terminal"
ferryd status --data-dir /var/lib/ferry
```

Starting a server that already runs changes nothing: `ferryd` prints where the running one listens. To start it with other options, stop it first.

### Stop and restart

Run `ferryd stop`, or press <kbd>Ctrl</kbd>+<kbd>C</kbd> in the terminal of a server in the foreground. Both shut the server down gracefully: open API requests get up to 10 seconds, then the engine stops running jobs and records deploys in progress as interrupted, within 25 seconds. A second `ferryd stop` (or a second <kbd>Ctrl</kbd>+<kbd>C</kbd>) while the server shuts down makes it exit at once.

Your app and datastore containers keep running in Docker while `ferryd` is stopped, but the proxy is part of `ferryd`, so their public URLs don't answer until it is back. On the next start, `ferryd` reads the same data directory, restores the routes and brings every service back to its desired state (see [Self-healing](/docs/concepts/self-healing)).

<Callout type="info" title="One server per data directory, one data directory per Docker prefix">
Only one `ferryd` can use a data directory at a time: it holds `ferryd.lock`. Each server also owns a Docker name prefix (`--name-prefix`, default `ferry`), recorded on a marker volume `<prefix>-owner`. A server refuses to start on a prefix that another data directory owns, so it can never remove another server's containers. To run several servers on one Docker daemon, give each its own prefix; see [Multiple servers](/docs/guides/multiple-servers).
</Callout>

## Configure for production

The defaults suit a laptop. On a server you will want a real base domain, HTTPS and a service manager. Most flags also have an environment variable; the most common ones:

| Flag | Environment variable | Default | Purpose |
|---|---|---|---|
| `--data-dir` | `FERRY_DATA_DIR` | `./ferry-data` | State of the server |
| `--base-domain` | `FERRY_BASE_DOMAIN` | `localhost` | Apps are served at `<name>.<base-domain>` |
| `--proxy-addr` | `FERRY_PROXY_ADDR` | `0.0.0.0:8080` | Public HTTP address, e.g. `0.0.0.0:80` |
| `--https-addr` | `FERRY_HTTPS_ADDR` | none | Public HTTPS address, e.g. `0.0.0.0:443` |
| `--acme-email` | `FERRY_ACME_EMAIL` | none | Enables Let's Encrypt certificates |
| `--github-webhook-secret` | `FERRY_GITHUB_WEBHOOK_SECRET` | none | Enables GitHub auto-deploys |

The [Production setup](/docs/guides/production) guide walks through a full setup with systemd, and [Server options](/docs/reference/server-options) lists every flag. If something doesn't start, see [Troubleshooting](/docs/guides/troubleshooting).
