Ferry reads Render's blueprint format. `ferry blueprint apply render.yaml` creates the env groups, databases, key value stores and services it describes, then deploys them. Keys Ferry doesn't support are ignored with a warning, never an error, so you can apply your file as it is and fix what the warnings list.

## Before you start

- A Ferry server with Docker, reachable at the domains you'll use. See [Production setup](/docs/guides/production).
- The `ferry` CLI logged in to it.
- The repositories your services build from must be reachable from the server: public, or with credentials in the URL, or over SSH. See [Auto-deploy from GitHub](/docs/guides/github-auto-deploy). A blueprint can't select a [connected GitHub or GitLab account](/docs/guides/git-accounts): to clone a private repository through one, choose the account in the service's settings after the first apply and deploy again. Later applies keep it.

## Migrate step by step

<Steps>
<Step>

### Preview the changes

Run a dry run from the directory that holds `render.yaml`. Without a file argument, `ferry blueprint apply` reads `./ferry.yaml`, then `./render.yaml`.

```bash title="Terminal"
ferry blueprint apply render.yaml --dry-run
```

```text title="Output"
Blueprint render.yaml — dry run, nothing was changed

Would create:
  + datastore shop-db
  + datastore shop-cache
  + service shop-web
  + service shop-worker

Warnings:
  ! blueprint: ignoring unsupported key 'previews'
  ! database 'shop-db': ignoring unsupported key 'region'
  ! database 'shop-db': ignoring unsupported key 'ipAllowList'
  ! service 'shop-web': autoDeployTrigger 'checksPass' is not supported; deploying on every commit
  ! service 'shop-web': ignoring unsupported key 'region'
  ! service 'shop-web': ignoring unsupported key 'preDeployCommand'
  ! service 'shop-web': ignoring unsupported key 'scaling'
  ! key value 'shop-cache': ignoring unsupported key 'ipAllowList'
  ! key value 'shop-cache': ignoring unsupported key 'maxmemoryPolicy'
  ! service 'shop-worker': registry credentials are not supported; the image must be pullable anonymously
  ! service 'shop-web': env var 'STRIPE_KEY' is marked sync: false; set it with `ferry env set shop-web STRIPE_KEY=...`

Run without --dry-run to apply.
```

Read every warning: each one is a Render feature your app won't get on Ferry. The [support matrix](#support-matrix) below explains them. Plans don't appear in the list: each `plan` becomes the resource limits of its service or datastore (see [Plans](#plans)). Only a plan Ferry doesn't know produces a warning (`ignoring unknown plan …`), and it sets nothing.

</Step>
<Step>

### Apply the blueprint

```bash title="Terminal"
ferry blueprint apply render.yaml
```

Ferry creates env groups first, then datastores (their provisioning starts in the background), then services. New services with a repository or an image get a first deploy (trigger `blueprint`). Follow them with `ferry deploys NAME` and `ferry logs --deploy ID -f`, and check the datastores with `ferry db ls`. If a first deploy fails because its database wasn't available yet, run `ferry deploy NAME` again.

`ferry show NAME` and `ferry db show NAME` print the `Memory limit` and `CPU limit` of a service or datastore, so you can check what its plan gave it.

</Step>
<Step>

### Set the values Render didn't sync

Variables marked `sync: false` aren't created. Set them yourself; each command restarts the service:

```bash title="Terminal"
ferry env set shop-web STRIPE_KEY=sk_live_…
```

</Step>
<Step>

### Move your Postgres data

Dump the Render database with its external URL, and load the dump into the Ferry datastore through its container (named `<prefix>-ds-<name>`, `ferry-ds-shop-db` by default). Run `pg_dump` from an image at least as recent as the Render server's Postgres version:

```bash title="Terminal"
docker run --rm postgres:16-alpine pg_dump --no-owner --no-acl "$RENDER_EXTERNAL_DATABASE_URL" > shop.sql
ferry db show shop-db    # prints the Database and User to load into
docker exec -i ferry-ds-shop-db psql -U shop_db shop_db < shop.sql
```

Replace `shop_db` with the `User` and `Database` that `ferry db show` prints. They come from `user` and `databaseName` in your `render.yaml`; without them, both default to the datastore name with `-` replaced by `_`, here `shop_db`.

Stop writes on Render while you copy, or plan a short maintenance window. Ferry has no import tool for Redis: key value stores start empty.

</Step>
<Step>

### Point your domains at Ferry

Add the DNS records of your custom domains (listed under `domains:` in the blueprint) pointing at the Ferry server. With [automatic HTTPS](/docs/concepts/networking#automatic-https) on, Ferry requests a certificate for each domain as soon as it resolves. See [Custom domains & HTTPS](/docs/guides/custom-domains-https).

</Step>
<Step>

### Turn on auto-deploy

Services with `autoDeploy` (on by default) redeploy on push once GitHub sends webhooks to Ferry. Follow [Auto-deploy from GitHub](/docs/guides/github-auto-deploy), and remove the Render service's webhook or disconnect it so a push doesn't deploy twice.

</Step>
</Steps>

## Support matrix

### Top level

| Key | On Ferry |
|---|---|
| `services` | Supported. |
| `databases` | Supported (Postgres). |
| `envVarGroups` | Supported. |
| `projects` / `environments` | Flattened: the resources of every environment are applied to this server, with a warning. |
| anything else (`previews`, …) | Ignored with a warning. |

### Service types

| Render `type` | Ferry |
|---|---|
| `web` | Web service. With `runtime: static` (or legacy `env: static`), a static site. |
| `pserv` | Private service. |
| `worker` | Background worker. |
| `cron` | Cron job. |
| `static` | Static site. |
| `redis`, `keyvalue` | A Redis datastore. Only `name` and `plan` are used (and Ferry's `memoryLimit` / `cpuLimit`); every other key, such as `ipAllowList` or `maxmemoryPolicy`, is ignored with a warning. |

### Service keys

| Key | On Ferry |
|---|---|
| `name`, `repo`, `branch`, `rootDir`, `dockerfilePath`, `buildCommand`, `startCommand`, `staticPublishPath`, `healthCheckPath`, `numInstances`, `autoDeploy`, `schedule`, `domains`, `envVars` | Supported, same meaning. |
| `runtime` (legacy `env`) | `docker`, `image`, `node`, `python`, `go`, `rust`, `ruby`, `static`. Another value (`elixir`…) falls back to auto-detection with a warning: add a Dockerfile. |
| `image` | `{url: …}` or a plain string. `creds` is ignored with a warning: the image must be pullable without credentials. |
| `dockerCommand` | Becomes the start command. If `startCommand` is also set, `startCommand` wins (with a warning). |
| `dockerContext` | Becomes the root directory, and `dockerfilePath` is made relative to it. Ignored with a warning when `rootDir` is set. |
| `autoDeployTrigger` | `commit` → auto-deploy on; `off` → off; `checksPass` → deploys on every commit, with a warning. |
| `disk` | `mountPath` is used; `name` and `sizeGB` are accepted and ignored (disks have no size limit). |
| `numInstances` on a cron job | Ignored with a warning. |
| `plan` | The memory and CPU limits of each instance and job run: see [Plans](#plans). Ignored on static sites, which have no plans on Render. |
| `port` | A Ferry extension: the port your app listens on. |
| `memoryLimit`, `cpuLimit` | Ferry extensions: set the limits directly, overriding the plan's. |
| anything else (`region`, `scaling`, `preDeployCommand`, `buildFilter`, `headers`, `routes`, …) | Ignored with a warning. |

### Environment variables

| Form | On Ferry |
|---|---|
| `{key, value}` | Set. Values are kept exactly as written: `3.10` stays `3.10`. |
| `{key, generateValue: true}` | A random 64-character hex value, generated only if the variable doesn't exist yet, so re-applying keeps it. |
| `{key, sync: false}` | Not set; a warning tells you the `ferry env set` command to run. |
| `{key, fromDatabase: {name, property}}` | A [reference](/docs/concepts/environment#references) `${{datastore.NAME.PROPERTY}}`, resolved when the service starts. |
| `{key, fromService: {type, name, property}}` | A reference to the service, or to the datastore for `type: redis` / `keyvalue`. |
| `{key, fromService: {name, envVarKey}}` | The other service's variable is **copied** at apply time. It isn't kept in sync afterwards. |
| `{fromGroup: NAME}` | Links the env group to the service (services only). |
| `previewValue` | Ignored with a warning. |

Properties for `fromDatabase` and key value stores: `connectionString`, `host`, `port`, `hostport`, `user`, `password`, `database`. For services: `host`, `port`, `hostport`, plus `url` and `internalUrl`.

### Databases

| Key | On Ferry |
|---|---|
| `name` | Supported. |
| `postgresMajorVersion` | The Postgres version (`postgres:<version>-alpine`); default `16`. |
| `databaseName`, `user` | Supported. |
| `plan` | The memory limit of the container: see [Plans](#plans). |
| `memoryLimit`, `cpuLimit` | Ferry extensions: set the limits directly, overriding the plan's. |
| anything else (`region`, `ipAllowList`, `readReplicas`, …) | Ignored with a warning. |

### Plans

Ferry has no instance types: a `plan` becomes the memory and CPU limits of the containers. Services get the plan's memory and CPU (`starter` → 512 MiB and 0.5 CPU, `standard` → 2 GiB and 1 CPU, `pro` → 4 GiB and 2 CPUs, and so on), except `free`, which gets 0.5 CPU instead of Render's 0.1. Postgres and Key Value plans set the memory only (`basic-1gb` → 1 GiB, Key Value `starter` → 256 MiB).

A resource without a plan or limit keys gets the server defaults: 512 MiB and 1 CPU per container, unless the server was started with other `--default-memory-limit` / `--default-cpu-limit` values. The [blueprint reference](/docs/reference/blueprint#plans) lists every plan, and the `memoryLimit` / `cpuLimit` keys that override them.

## How re-applying works

You can apply the same file again after editing it:

- Nothing is ever deleted. A resource you remove from the file stays on the server.
- Existing services are updated in place; the result lists `create`, `update` (with the changes) and `unchanged`.
- A service whose build or deploy settings changed is deployed again. A service whose only changes are its resource limits (a new `plan`, `memoryLimit` or `cpuLimit`) or its variables is restarted, if it is live: nothing is rebuilt.
- Limits the file doesn't set (no `plan`, `memoryLimit` or `cpuLimit`) are kept, like `numInstances`: changes you made with `ferry update --memory` or in the dashboard stay.
- Existing datastores keep their version, database name and user: a different value in the file only produces a warning. Their limits do change, in place and without a restart.
- `--dry-run` shows all of this without changing anything, including limit changes such as `memory_limit: 512 MiB → 2 GiB`.

The [blueprint reference](/docs/reference/blueprint) documents every key, including Ferry's own `ferry.yaml` usage.

## Differences to keep in mind

- **Language versions** come from your project files, not from variables: `engines.node` in `package.json`, `.python-version` or `runtime.txt`, the `go` line of `go.mod`, `.ruby-version` or the `Gemfile`. `NODE_VERSION` or `PYTHON_VERSION` variables are passed to your app like any other variable. See [Language guides](/docs/guides/language-guides).
- **Pre-deploy commands** don't exist. Run migrations with a one-off job: `ferry run NAME -- npm run migrate`. See [Deploy an app with Postgres](/docs/guides/postgres-app#run-migrations-on-every-deploy).
- **Plans are limits, not machines**, and regions don't apply: everything runs on your server. A plan's limits are caps, not reservations: nothing checks that they fit the server, and a CPU limit above its CPU count is capped at it. Size the server for what you run; see [Resource limits](/docs/concepts/resource-limits).
- **Key value stores** ignore `maxmemoryPolicy`: Ferry sets Redis's `maxmemory` to 3/4 of the store's memory limit, and a full Redis refuses writes. Give a cache enough memory with its `plan` or `memoryLimit`.
- **The port** works like Render: Ferry injects `PORT` (default `10000`) and routes to it.
- **Static sites** are served by nginx with `try_files $uri $uri/ $uri.html` and your `404.html`. Render's `routes` (redirects and rewrites) and `headers` aren't supported.
- **Also not in Ferry:** pull request previews, autoscaling, private registry credentials, secret files and IP allow lists.
