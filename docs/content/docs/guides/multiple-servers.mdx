Several `ferryd` processes can share one Docker daemon, for example a staging and a production server on the same machine, or a throwaway server for tests next to your real one. Each server must have its own:

| What | Option | Why |
|---|---|---|
| Data directory | `--data-dir` | Its database, logs and certificates. A data directory is locked by the server using it. |
| Name prefix | `--name-prefix` | Every Docker resource of the server carries it. It must be unique per daemon. |
| API address | `--api-addr` | Two servers can't listen on the same port. |
| Proxy addresses | `--proxy-addr`, `--https-addr` | Same. Only one server can own ports 80 and 443. |
| Base domain | `--base-domain` | So their apps don't answer to the same hostnames. |

## What the name prefix covers

The prefix (default `ferry`) is part of every Docker name and label a server creates:

| Resource | Name |
|---|---|
| Private network | `<prefix>` |
| Service containers | `<prefix>-<service>-<deploy>-<random>` |
| Job containers | `<prefix>-job-<service>-<job>` |
| Datastore containers and volumes | `<prefix>-ds-<name>`, `<prefix>-ds-<name>-data` |
| Service disks | `<prefix>-svc-<service id>-disk` |
| Built images | `<prefix>/<service>:<deploy id>` |
| Ownership marker volume | `<prefix>-owner` |

Every container also has the label `ferry.instance=<prefix>`, and a server only lists and manages containers with its own prefix. Its reconciler removes containers under that prefix that it doesn't know about, which is why two servers must never share a prefix: each would delete the other's apps as orphans.

Servers with different prefixes are isolated from each other: separate networks, so their services can't reach each other by name, and separate images and volumes.

## Run a second server

```bash title="Terminal"
# production (defaults: prefix ferry, API :7878, proxy :8080)
ferryd --data-dir /var/lib/ferry

# staging, on the same Docker daemon
ferryd --data-dir /var/lib/ferry-staging \
  --name-prefix staging \
  --api-addr 127.0.0.1:7879 \
  --proxy-addr 0.0.0.0:8081 \
  --base-domain staging.localhost
```

Apps of the staging server are at `http://<name>.staging.localhost:8081`. On a public server, give the second server its own base domain (`--base-domain staging.example.com`) and put it behind a different port or another IP address.

The CLI saves one server in its config. Point a command at another server with flags or environment variables, which take precedence over the saved config:

```bash title="Terminal"
FERRY_SERVER=http://127.0.0.1:7879 FERRY_TOKEN=$(cat /var/lib/ferry-staging/api_token) ferry ls
ferry --server http://127.0.0.1:7879 --token fy_… ls
```

## The safety checks

**A data directory runs one server at a time.** `ferryd` holds a lock on `<data-dir>/ferryd.lock`:

```text
Error: another ferryd is already running with data directory /var/lib/ferry
```

**A prefix belongs to one data directory.** The first time a server starts, it writes its identity (`<data-dir>/instance_id`) and its data directory on the marker volume `<prefix>-owner`. A server with another data directory then refuses the prefix:

```text
Error: Docker resources with prefix 'ferry' belong to another Ferry server (data dir /var/lib/ferry). Run this server with a different --name-prefix, stop the other server, or pass --take-over to adopt the resources (the other server's containers will then be managed — and possibly removed — by this one).
```

It also refuses when its data directory is empty and it finds containers under its prefix that no marker explains. This catches the common mistake of starting `ferryd` from another directory with the default `./ferry-data`:

```text
Error: found 3 Docker container(s) with prefix 'ferry' that this (empty) data dir /home/you/projects/ferry-data doesn't know. They probably belong to another Ferry server. Run this server with a different --name-prefix, …
```

## Move a server to another data directory

To move the data directory on the same machine:

1. Stop `ferryd`.
2. Move or copy the whole directory, keeping its permissions (`0700`, owned by the user that runs `ferryd`).
3. Start `ferryd` with the new `--data-dir` and **the same** `--name-prefix`. The directory's `instance_id` moved with it, so the server still owns the prefix, and it manages its running containers again.

If the server refuses the prefix, because `instance_id` didn't come along (for example, you restored only `ferry.db`), start it once with `--take-over`: it replaces the marker with its own identity. Never use `--take-over` to start a second server on a prefix that another running server uses: the new server would treat the other one's containers as orphans and remove them.

## Remove a server

Delete its services and datastores first (`ferry delete`, `ferry db rm`), then stop it. To clean up everything that is left under its prefix:

```bash title="Terminal"
docker ps -aq --filter label=ferry.instance=staging | xargs docker rm -f
docker volume ls -q --filter label=ferry.instance=staging | xargs docker volume rm
docker image ls --filter reference='staging/*' --format '{{.Repository}}:{{.Tag}}' | xargs docker rmi
docker network rm staging
```

Remove the images by name, as above, not by image id: a server tags every image it pulls under its own prefix (`staging/web:dep-…` for `nginx:alpine`, say), and deleting by id would also delete the original image and every other tag that shares it.

<Callout type="danger" title="This deletes data">
The volumes hold the server's datastores and disks. Back them up first if you need them.
</Callout>
