Each section below starts with the message you see, then gives its cause and the fix. Messages are quoted as Ferry prints them; `…` stands for the parts that depend on your setup. For a failed deploy, the full story is in its log: `ferry logs --deploy DEPLOY_ID`, or the deploy's page in the dashboard.

## Starting ferryd

`ferryd` checks its data directory, its listen addresses and Docker before it starts anything. When one of them fails, it exits with an `Error:` line and its cause.

### ferryd can't connect to Docker

```text title="ferryd" noCopy
Error: cannot connect to Docker — is the Docker daemon running?

Caused by:
    docker error: cannot connect to the Docker daemon (unix:///var/run/docker.sock: …)
```

**Cause:** Docker isn't running, its socket is somewhere else (Colima, OrbStack, rootless Docker), or your user isn't allowed to open it. The cause lists every socket `ferryd` tried.

**Fix:** start Docker, and point `DOCKER_HOST` at the right socket if needed: see [How ferryd finds Docker](/docs/getting-started/installation#how-ferryd-finds-docker). On Linux, run `ferryd` as a user in the `docker` group.

If the cause is `unsupported DOCKER_HOST '…' (use unix://, tcp:// or http://)`, your `DOCKER_HOST` uses `ssh://` or another scheme Ferry doesn't support (TLS isn't supported either). Use the daemon's Unix socket (`unix://…`) or a plain `tcp://` address on the same machine.

### A port is already in use

```text title="ferryd" noCopy
Error: cannot listen on 0.0.0.0:80 (proxy address)

Caused by:
    Address already in use (os error 98)
```

**Cause:** another program, often a web server, already listens on that address. The message says which one: `proxy`, `HTTPS proxy` or `API`. (The error number differs between systems: `98` on Linux, `48` on macOS.)

**Fix:** stop the other program, choose another address with `--proxy-addr`, `--https-addr` or `--api-addr`, or run Ferry [behind the existing reverse proxy](/docs/guides/production#behind-an-existing-reverse-proxy). To see which program holds the port:

<Tabs items={['Linux', 'macOS']}>
<Tab value="Linux">
```bash title="Terminal"
sudo ss -ltnp 'sport = :80'
```
</Tab>
<Tab value="macOS">
```bash title="Terminal"
sudo lsof -nP -iTCP:80 -sTCP:LISTEN
```
</Tab>
</Tabs>

### Permission denied on port 80 or 443

```text title="ferryd" noCopy
Error: cannot listen on 0.0.0.0:80 (proxy address)

Caused by:
    Permission denied (os error 13)
```

**Cause:** on Linux, only privileged processes may listen on ports below 1024.

**Fix:** give `ferryd` the `CAP_NET_BIND_SERVICE` capability instead of running it as root: `AmbientCapabilities=CAP_NET_BIND_SERVICE` in its systemd unit (see [Production setup](/docs/guides/production#write-the-configuration)), or `sudo setcap cap_net_bind_service=+ep /usr/local/bin/ferryd`, which you repeat after each upgrade.

### Another ferryd uses the data directory

```text title="ferryd" noCopy
Error: another ferryd is already running with data directory /var/lib/ferry
```

**Cause:** a second `ferryd` was started with the same `--data-dir`. Only one server can use a data directory at a time.

**Fix:** stop the other process, or give this one its own data directory.

### The Docker prefix belongs to another server

```text title="ferryd" noCopy
Error: Docker resources with prefix 'ferry' belong to another Ferry server (data dir /var/lib/ferry). Run this server with a different --name-prefix, stop the other server, or pass --take-over to adopt the resources (…)
```

A variant says `found N Docker container(s) with prefix 'ferry' that this (empty) data dir … doesn't know`.

**Cause:** each Docker name prefix belongs to one data directory. This server's data directory isn't the one that owns `ferry`. Typically, `ferryd` was started from another folder with the default `./ferry-data`, or two servers share one Docker daemon.

**Fix:** start `ferryd` with the data directory that owns the prefix (named in the message), or give this server its own `--name-prefix`. See [Multiple servers](/docs/guides/multiple-servers).

<Callout type="warning" title="Don't reach for --take-over">
A data directory you moved keeps its `instance_id` and starts with the same `--name-prefix` without any extra flag. Use `--take-over` only for a data directory that lost its `instance_id`, and never while another server uses the prefix: the server that takes over removes the other server's containers.
</Callout>

## Signing in to the dashboard

### The dashboard asks for a setup code

The dashboard opens on **Create your account**, with an empty **Setup code** field, or refuses the code:

```text title="Dashboard" noCopy
This is not the setup code of this server.
```

**Cause:** the server has no account yet, and creating it takes the setup code, so that only someone who can read the server's terminal or data directory can do it. The link `ferryd` prints fills the code in; the dashboard was opened without that link, or with the link of another server.

**Fix:** on the server, run `ferryd status` (with the same `--data-dir` as the server). While there is no account, it ends with the link:

```text title="ferryd status" noCopy
  Create your account: http://127.0.0.1:7878/setup?code=5b0e…
```

Open the link, or copy its code into the field. The code is also in `<data-dir>/setup_code`. See [Create your account](/docs/getting-started/installation#create-your-account).

### I forgot the password

**Cause:** the password can't be read back: the server only stores a hash of it.

**Fix:** choose a new one on the server, with [`ferryd reset-password`](/docs/reference/server-options#ferryd-reset-password). Run it as the user that runs `ferryd`, with the server's data directory:

```bash title="Terminal"
sudo -u ferry ferryd reset-password --data-dir /var/lib/ferry
```

It asks for the new password twice, without showing it, then signs every browser out. It works while the server runs, and API tokens keep working. When its input isn't a terminal, it reads the new password from one line of standard input instead.

### Too many failed attempts

```text title="Dashboard" noCopy
too many failed attempts: try again in 4 minutes
```

**Cause:** 10 sign-ins failed within 5 minutes. The limit counts for the whole server, not per address, so the failures may not be yours.

**Fix:** wait: sign-ins are accepted again once the oldest failure is 5 minutes old. If it keeps happening, someone else is trying to sign in: keep the API on `127.0.0.1` and reach it through an SSH tunnel. See [Security model](/docs/architecture/security#the-account).

## Connecting the CLI

### The CLI can't reach the server

```text title="ferry" noCopy
Error: cannot reach Ferry server at http://127.0.0.1:7878 — is ferryd running?
```

**Cause:** nothing answers at that address: `ferryd` is stopped, the URL is wrong, or the server is remote and the SSH tunnel is closed.

**Fix:** start `ferryd`, check `--server` or `FERRY_SERVER`, or open the tunnel with `ssh -N -L 7878:127.0.0.1:7878 you@your-server`.

### Not logged in, or the token is wrong

```text title="ferry" noCopy
error: not logged in: run 'ferry login --server <URL>' first (or set FERRY_SERVER and FERRY_TOKEN)
```

```text title="ferry" noCopy
error: invalid API token (unauthorized)
hint: the token was refused (revoked or expired?): log in again with 'ferry login --server <URL>'
```

**Cause:** there is no saved login and no `--token` or `FERRY_TOKEN`, or the server refuses the token: it was revoked in the dashboard, it has expired, or it belongs to another server (for example, the server now runs with another data directory).

**Fix:** run `ferry login --server <URL>` again and approve the request in the dashboard. For CI and scripts, create a new API token under **Server → Account** and put it in `FERRY_TOKEN`. See [Set up the CLI](/docs/getting-started/cli#log-in). A direct API call without credentials gets `401` with `not signed in: send an API token as 'Authorization: Bearer <token>', or sign in to the dashboard`: send `-H "Authorization: Bearer $FERRY_TOKEN"`.

### ferry login doesn't finish

```text title="ferry" noCopy
error: the login request expired before it was approved: run 'ferry login' again
```

**Cause:** `ferry login` waits until you approve its request in the dashboard, and a request expires after 10 minutes.

**Fix:** run `ferry login` again, open the page it prints, sign in, check that the page shows the code of your terminal and click **Approve**. Where nobody can open the dashboard (CI, a script), log in with a token instead: see [Log in with a token](/docs/getting-started/cli#log-in-with-a-token).

On a new server, `ferry login` stops at once instead:

```text title="ferry" noCopy
error: this server has no account yet: create it in the dashboard first (`ferryd status` prints the link) (conflict)
```

Create the account first: see [Create your account](/docs/getting-started/installation#create-your-account).

## Builds

A failed build ends the deploy as `build_failed`. The live deploy keeps serving.

### Ferry can't detect the runtime

```text title="Deploy log" noCopy
could not detect the runtime: add a Dockerfile, or a package.json, requirements.txt, pyproject.toml, Pipfile, go.mod, Cargo.toml, Gemfile or index.html, or set the runtime explicitly
```

**Cause:** the build context has no file that tells Ferry how to build the app.

**Fix:** add a `Dockerfile` or your language's manifest, set `--root-dir` when the app lives in a subdirectory, or choose the runtime with `--runtime`. See [Builds & runtimes](/docs/concepts/builds).

### Builds fail on an older Docker Engine

```text title="Deploy log" noCopy
… (secret env mounts need Docker Engine 27.3 or newer: upgrade Docker on the Ferry server)
```

**Cause:** the service has environment variables, which reach the build as BuildKit secrets, and the Docker Engine is older than 27.3.

**Fix:** upgrade Docker on the server.

### The docker CLI isn't found

```text title="Deploy log" noCopy
the docker CLI ('docker') was not found: install Docker on the Ferry server
```

**Cause:** `ferryd` runs `docker build`, and there is no `docker` command on its `PATH`. Service managers sometimes start it with a minimal `PATH`.

**Fix:** install the Docker CLI, or pass its full path with `--docker-bin`.

### The disk is nearly full

```text title="Deploy log" noCopy
==> Build failed: not enough free disk space on /var/lib/ferry: 812 MiB free, Ferry needs at least 1 GiB (free some space, e.g. remove unused Docker images with `docker image prune`, or change the threshold with `ferryd --min-free-disk`, 0 = off)
```

**Cause:** the filesystem of the data directory, or of Docker's root directory, has less free space than `--min-free-disk` (1 GiB by default). Ferry checks it before a deploy builds or pulls, and before it creates a new datastore, which then fails with the same message. Restarts and rollbacks aren't checked.

**Fix:** free some space: `docker image prune` removes unused images, and `docker builder prune` the build cache. See [Free disk space](/docs/concepts/resource-limits#free-disk-space).

## Deploys

A deploy that fails ends as `deploy_failed`, and the previous deploy keeps serving. See [Deploys](/docs/concepts/deploys#health-checks) for how health checks work.

### The health check times out

```text title="Deploy log" noCopy
==> Deploy failed: health check timed out after 120s: nothing accepts connections on container port 10000 (published as 127.0.0.1:…) yet: does the app listen on $PORT (10000) on 0.0.0.0? An app listening on 127.0.0.1 (localhost) inside its container can't be reached
```

**Cause:** the app listens on `127.0.0.1` inside its container, or on a fixed port instead of `$PORT`. If you set `PORT` yourself to another value than the service's port, the message says `the app gets PORT=… from its environment but Ferry expects it to listen on port …` instead.

**Fix:** listen on `0.0.0.0` and on the port in `$PORT`, or set the port your app uses with `ferry update NAME --port N`. See [Environment](/docs/concepts/environment#the-port-variable). An app that just needs more time to start can get it from a longer timeout for the whole server: `ferryd --health-check-timeout`.

### The health check path answers with an error

```text title="Deploy log" noCopy
==> Deploy failed: health check timed out after 120s: GET /healthz returned HTTP 404
```

**Cause:** the health check path (`--health`) doesn't exist in the app, or answers with a status of 400 or more.

**Fix:** correct the path with `ferry update NAME --health /path`, or clear it with `--health ""`.

### The app crashes

```text title="Deploy log" noCopy
==> Deploy failed: instance d1c6b8 crashed (exit code 1)
```

**Cause:** the app exited while Ferry waited for its health check. Some exit codes add a hint, such as `127: command not found, check the start command`.

**Fix:** read the instance's last lines of output, which Ferry copies into the deploy log just above.

### The app exits right away

```text title="Deploy log" noCopy
==> Start command: node ./dist/index.js (package.json has no "start" script: its "main" file is run)
…
==> Deploy failed: instance 2e58a7 exited with code 0: its command `node ./dist/index.js` ended without an error, but a web service must keep running and listen on port 10000
==> Hint: the service has no start command, so Ferry picked this one from the project (see "==> Start command" in the build log). If the project is an app, set the start command that runs its server. If it only builds files (a static site, a component library), create it as a static site instead.
```

**Cause:** the command the instance ran finished without an error, and often without printing anything, instead of starting a server that keeps running. The message names that command, and the hint says where it comes from:

| The command is | Typical case | Fix |
|---|---|---|
| picked from the project, because the service has no start command | A library, or a site that only builds files: its `main` file loads and returns | Create the service as a **static site** with its build command and publish directory, or set the start command of the app's server |
| the service's start command | It only builds (`npm run build`), or starts a daemon and returns | Put build steps in the build command; start the server in the foreground |
| the image's own command | An image made for one-shot tasks | Set a start command on the service |

A background worker that ends is told the same way: a task that runs and ends belongs in a [cron job or a one-off job](/docs/concepts/jobs) (`ferry run`).

### The app runs out of memory

```text title="Deploy log" noCopy
==> Deploy failed: instance d1c6b8 ran out of memory (limit 512 MiB) — raise the service's memory limit
```

**Cause:** the new instance used more memory than its limit (the server's default, 512 MiB, unless the service sets its own), and the kernel killed it. Once a deploy is live, the same kill makes Docker restart the instance: `ferry status NAME` shows it as `restarting (OOM killed, exit code 137)`, and `ferryd` logs it.

**Fix:** raise the limit, then deploy again (`ferry up NAME` for local code):

```bash title="Terminal"
ferry update NAME --memory 1G
ferry deploy NAME
```

When it's the live instances that keep getting killed, `ferry restart NAME` gives them the new limit without a rebuild. See [Out-of-memory kills](/docs/concepts/resource-limits#out-of-memory-kills).

## Reaching your app

When the proxy can't forward a request, it answers with its own page and an `x-ferry-error` header, so you can tell it apart from your app's errors:

```bash title="Terminal"
curl -sI http://shop.localhost:8080/ | grep -i x-ferry-error
```

| Status and `x-ferry-error` | Cause | Fix |
|---|---|---|
| `404` `not_found` | No service owns this hostname: a typo, a base domain other than `--base-domain`, a request by IP address, a worker or private service (they have no public URL), or a reverse proxy in front of Ferry that doesn't pass the `Host` header. | Get the URL with `ferry open NAME`. For custom domains, check `ferry domains NAME`. |
| `503` `no_upstreams` | The service has no running instance: it was never deployed, its last deploy failed, or its first deploy is still running. | Check `ferry deploys NAME` and `ferry status NAME`, then read the failed deploy's log. |
| `503` `suspended` | The service is suspended. | `ferry resume NAME` |
| `502` `bad_gateway` | The instance refused the connection or failed in the middle of the request. | Read the runtime logs: `ferry logs NAME`. |

For certificates and custom domains, see the troubleshooting table in [Custom domains & HTTPS](/docs/guides/custom-domains-https#troubleshooting).
