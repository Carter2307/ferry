A <Term id="blueprint" /> describes your <Term id="env-group">env groups</Term>, your <Term id="postgres" /> databases, your <Term id="redis" /> datastores and your <Term id="service">services</Term> in one <Term id="yaml" /> file.

An <Term id="apply" /> creates what is not there and updates what changed. It never deletes. A second apply of the same file changes nothing.

Ferry reads the `render.yaml` format of <Term id="render" />, with its <Term id="camel-case" /> keys. It supports a practical part of this format. Ferry ignores a key that it does not support, with a warning and never an error. Thus a `render.yaml` that you have applies as it is. The `plan` of Render becomes the [resource limits](/docs/reference/blueprint/limits) of the containers.

## Apply a blueprint

```bash title="Terminal"
ferry blueprint apply --dry-run   # show what would change
ferry blueprint apply             # apply ./ferry.yaml, else ./render.yaml
```
